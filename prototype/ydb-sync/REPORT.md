## 0. Итог на одной странице

| Вопрос | Ответ |
|---|---|
| Подходит ли YDB Serverless? | **Да.** Нужные операции реализованы и проверены на локальной YDB: атомарная пачка, атомарные версии под конкуренцией, pull по курсору без пропусков, только точечные и диапазонные чтения (стоимость не растёт с историей пользователя), TTL, транзакции до 20 000 мутаций. |
| Какая sync-модель? | **Вариант B:** серверная монотонная версия + `baseVersion` от клиента + delete wins. Конкурентный конфликт решает `updatedAt` (обрезка до now+5 мин) с монотонной меткой записи на сервере. |
| Нужен ли HLC? | **Нет.** Единственное, что HLC даёт сверх простого LWW, — правильный порядок причинно связанных правок при неверных часах. `baseVersion` решает ту же задачу без участия часов. В симуляции на 1000 историях у варианта B и HLC одинаково 0 потерь причинно-более-поздних правок, а без того и другого — 693 потери (§3). |
| Риск потери данных | Подтверждённые изменения не теряются, удалённые записи не воскресают, повторы не создают дубликатов. Проверено 15 сценариями ×2 стратегии и 1000 рандомизированными историями (~107 тыс. правок на стратегию): **0 нарушений** у выбранной модели. По дороге найдены и исправлены 4 дефекта, которые без тестов привели бы к тихой потере или расхождению (§4.2). Остаточный, принятый по дизайну риск: при *конкурентной* правке одной записи с двух устройств побеждает более поздняя по часам, проигравшая отбрасывается целиком (LWW по записи). При неверных часах «более поздняя» может оказаться не той. |
| Ограничения | (1) Локальная YDB **не тарифицирует записи**, поэтому RU push — пока прогноз [Ф], главная цифра облачного этапа. (2) Все push одного пользователя сериализуются на строке `sync_state`: до 16 одновременных проходят, при 24 часть получает `503` и повторяет. (3) **Хранение ≈ 900 Б на запись** против ~500 Б в документе. (4) Лимит YDB по умолчанию 10 RU/с меньше, чем стоит одна первичная выгрузка 1000 записей (≈6000 RU). |

| Корректировать архитектуру? | **Да, точечно, без смены стека:** delete wins вместо LWW для удалений, `baseVersion` вместо HLC, правило «правка того же устройства», полная запись в ответе на повтор, `503` при исчерпании повторов, явный `GLOBAL SYNC` индекс, политика хранения tombstones и истории, лимит RU/с ≥ 100–300 с первого дня (§8). |

## 1. Что сделано

- **Изолированный прототип** `prototype/ydb-sync/`: FastAPI (`/health`, `POST /sync/push`, `GET /sync/pull`), YDB через официальный SDK (`ydb` 3.33, Query Service, async), схема `sync_records` / `sync_state` / `sync_mutations`.
- **Тестовый клиент** — модель iOS local-first: SQLite, outbox и курсор в том же файле (переживают перезапуск), перебазирование после подтверждения. Транспорт умеет имитировать offline, потерю ответа после коммита на сервере и обрыв посреди страниц pull.
- **Четыре стратегии конфликтов** в одном движке: базовая линия `lww_clock`, вариант A из документа `hlc`, `hlc_dw` (A + delete wins), вариант B `version`. Отдельные backend-ы не строились.
- **60 автоматических тестов**, все проходят. Симуляция на 1000 историй, benchmark, модель стоимости, Docker-образ, конфигурация облачного этапа, отдельный CI workflow (`.github/workflows/prototype-ydb-sync.yml`, запускается только при изменениях в прототипе).

Окружение измерений: MacBook (arm64), `ydbplatform/local-ydb:latest`. Официальный образ только amd64, поэтому YDB работает **под эмуляцией Rosetta** в colima, PDisk в памяти. Latency и CPU отсюда **нельзя переносить на облако** (§5).

## 2. Протокол

Push — одна serializable-транзакция YDB, **ровно 2 обращения** [И]:
1. Чтение, которое открывает транзакцию: `sync_state` пользователя, `sync_mutations` по списку `mutationId`, `sync_records` по списку ключей через `JOIN AS_TABLE($keys)` (lookup по PK).
2. Чистая функция `plan_push` в Python решает судьбу каждой мутации и назначает версии `last_version + 1…`.
3. Один запрос записи (`UPSERT` записей, журнала и `sync_state`) с `commit_tx`. Если все мутации — повторы, вместо записи выполняется rollback.

При `ABORTED` (конкурентный push того же пользователя изменил `sync_state`) SDK повторяет **весь** цикл, включая планирование. Поэтому порядок версий совпадает с порядком коммитов, и pull по курсору не может перепрыгнуть ещё не закоммиченную меньшую версию. Это проверено тестом с конкурентным pull [И].

Pull — один запрос в snapshot read-only транзакции: `sync_state` (горизонт tombstones) + `SELECT … FROM sync_records VIEW by_version WHERE user_id=$u AND version > $cursor ORDER BY version LIMIT $limit+1`.

Правила варианта B (`syncproto/resolve.py`):
1. Запись удалена: правка отклоняется (`deleted`), повторное удаление — `noop`. Tombstone окончателен.
2. Удаление применяется всегда (delete wins).
3. Текущая запись получена этой же мутацией → `noop`. Так безопасен повтор и после истечения 30-дневного журнала.
4. `baseVersion == current.version` или текущая версия — предыдущая правка **того же устройства** → применить. Часы не участвуют.
5. Иначе это конкурентный конфликт: побеждает больший (`min(updatedAt, now+5 мин)`, `deviceId`) против монотонной метки записи `order_ts`. Проигравший получает `rejected/conflict` и актуальную запись.

Клиент (`client/client.py`):
- удаляет мутацию из outbox только по ответу сервера;
- повторяет с теми же `mutationId` в том же порядке;
- после `applied` перебазирует свои следующие мутации этой записи;
- не перетирает запись с неотправленной мутацией при pull: конфликт решит сервер;
- сохраняет страницу pull и курсор одной локальной транзакцией.

## 3. Вариант A (HLC + LWW) против варианта B (версия + baseVersion)

### 3.1. Рандомизированная симуляция [И]

`python -m client.simulate --seeds 1000`, результат в `bench/results/simulation_1000.json`. В каждой истории 2–4 устройства, часы сдвинуты на 0 / ±20 с / ±5 мин / ±2 ч / ±1 сутки, есть offline-периоды, 10 % потерянных ответов push и обрывы pull. После затишья все устройства синхронизируются. Происхождение каждой правки отслеживается меткой в payload.

| Стратегия | Правок | Расхождение устройств | Воскрешённые удаления | Потеряна причинно-более-поздняя правка | Конкурентный конфликт решён «не той» по реальному времени (часы) |
|---|---:|---:|---:|---:|---:|
| `lww_clock` (LWW по часам, без HLC) | 107 102 | 0 | **479** | **693** | 761 |
| `hlc` (A, как в документе §8.2–8.4) | 107 112 | 0 | **547** | 0 | 711 |
| `hlc_dw` (A + delete wins) | 107 113 | 0 | 0 | 0 | 625 |
| **`version` (B)** | 107 113 | 0 | 0 | 0 | 666 |

Выводы:
- **Воскрешение удалений** — дефект самого документа: «удаление против редактирования решается тем же LWW» (§8.4). Офлайн-правка с более поздним временем возвращает удалённый расход. Исправление — delete wins, оно нужно в любом варианте.
- **Причинно-более-поздние правки** теряет только LWW по часам. HLC и `baseVersion` устраняют это одинаково.
- **Конкурентные правки при неверных часах** неизбежно решаются по часам в любой LWW. Цифры A и B сопоставимы (625 и 666 на ~107 тыс. правок), HLC здесь не помогает.

### 3.2. Какую проблему решает HLC и почему она решается проще

Сценарий из `tests/test_resolve.py::test_wall_clock_lww_loses_causally_later_edit_hlc_and_version_do_not`:
- телефон с верными часами правит расход в 12:00;
- планшет, часы которого отстают на 10 минут, получает эту правку и **после неё** (реально в 12:01) меняет сумму. Его `updatedAt` = 11:51.
- **LWW по часам** отклоняет правку планшета: 11:51 < 12:00. Пользователь видит, что его исправление пропало.
- **HLC**: при получении записи планшет делает `HLC = max(свои часы, увиденный HLC) + 1`, поэтому его правка больше. Нужно хранить состояние HLC персистентно и обновлять его на каждом pull и ответе push.
- **Вариант B**: планшет отправляет `baseVersion` = версию правки телефона. Сервер видит, что правка основана на актуальном состоянии, и применяет её. Часы не участвуют вообще.

Сценарий, который HLC решает, а `baseVersion` — нет, существует только без единого сервера-арбитра: peer-to-peer sync между устройствами или несколько независимых серверов. В нашей архитектуре один арбитр — YDB, поэтому **HLC не нужен**.

### 3.3. Сравнение по критериям

| Критерий | A: HLC + LWW | B: версия + baseVersion |
|---|---|---|
| Сложность реализации | Сервер: сравнение и обрезка HLC. Клиент: персистентные HLC-часы, `observe` на каждом pull и ответе push. Нужны те же правила delete wins и «то же устройство» (§4.2) | Сервер: сравнение версии и правило конфликта (~30 строк). Клиент: хранить серверную версию записи (уже приходит в pull) и перебазировать outbox после подтверждения |
| Неправильные часы устройства | Причинный порядок сохраняется, если клиент корректно ведёт HLC. Сутки вперёд — после обрезки до now+5 мин побеждает в конкурентных правках в окне 5 мин. Отрицательный сдвиг — проигрывает конкурентные | Причинный порядок вообще не зависит от часов. Конкурентные правки — так же, как в A |
| Два устройства offline | Сходятся по LWW | Сходятся. Конфликт **явно обнаруживается** (`conflict: true`), его можно показать в UI и посчитать в метриках |
| Конкурентное редактирование | LWW по HLC, порядок прихода не важен | LWW по `updatedAt` с монотонной меткой. Тест 13: все 6 перестановок трёх конкурентных правок дают одно состояние [И] |
| Удаление против правки | В документе — LWW, удаления **воскресают** (547 в симуляции). С delete wins — корректно | Delete wins встроено |
| Риск потери | Зависит от корректности HLC на каждом клиенте: забытый `observe` после pull снова даёт потерю причинно-поздних правок | Ошибка клиента с `baseVersion` даёт лишний конфликт, а не тихую потерю: конфликт решается по часам и попадает в метрику |
| Поддержка | Формат HLC, допуск обрезки, миграция HLC при переустановке, отладка «почему победила эта правка» по синтетическим меткам | Версии — обычные целые числа сервера, отладка по журналу версий. Правка на стороне сервера (миграции данных, слияние аккаунтов) не требует генерации HLC |

**Выбор: вариант B.**

Цена выбора: переход на LWW по полям в будущем в варианте A проще (HLC на поле). В B для этого понадобятся версии на поле. Протокол это допускает, но это отдельная работа.

### 4.2. Найденные проблемы

Первые четыре нашла симуляция. Все исправлены, на каждую есть регрессионный тест.

| Проблема | Последствие | Исправление |
|---|---|---|
| Повтор **отклонённой** мутации после потери ответа возвращал сохранённый `rejected` без актуальной записи | Устройство навсегда оставалось со своей отклонённой правкой: **расхождение с сервером** | Для любого повтора, кроме `applied`, всегда прикладывается актуальная запись |
| Повтор применённой мутации, когда запись уже изменило другое устройство | Клиент «застревал» на своей версии: курсор уже прошёл чужую | В ответ прикладывается актуальная запись (`test_06b`) |
| Обрезка будущего времени (now+5 мин, как в документе) делает две последовательные правки устройства со спешащими часами **равными** | Вторая молча становилась `noop`: **тихая потеря**. Затрагивает и A, и B | `noop` только при совпадении `mutationId`. Правка того же устройства всегда новее (outbox — FIFO) |
| Перебазирование внутри пачки работало на один шаг | create → edit → edit в одной пачке: третья правка решалась как конфликт и могла потеряться | Исходная база сохраняется на всю цепочку |
| LWW для удалений (документ §8.4) | Воскрешение удалённых записей | Delete wins |
| 24 одновременных push одного пользователя | Часть транзакций исчерпывает 15 повторов OCC | `503` + `Retry-After`: push идемпотентен, клиент повторяет |
| Discovery локальной YDB отдаёт `localhost:2136` | Соседний контейнер не подключается (fail fast при старте) | В compose `api` делит сеть с `ydb`. В облаке не применимо |

Исправление собственной ошибки: сначала я сделала вывод, что вариант `WHERE (entity_type, entity_id) IN $keys` сканирует историю пользователя (19 RU против 2). Перепроверка показала, что это стоимость **компиляции** запроса при первом выполнении (CPU ≈ 29 мс, RU = max(CPU, IO)). После прогрева оба варианта стоят одинаково, а план — точечные чтения (`ReadRangesPointPrefixLen = 3`). Тест исправлен и меряет после прогрева.

### 5.2. Реализуемы ли транзакции документа

Да, «пачка одной serializable-транзакцией» реализуема как описано, но с уточнениями, которых в документе нет:
- версия назначается чтением `sync_state` **в той же транзакции**, и при `ABORTED` повторяется всё, включая логику разрешения. Повторять только запись нельзя;
- pull должен идти в snapshot read-only (или serializable), не в stale read-only, а индекс — `GLOBAL SYNC`. С `ASYNC` или stale-чтением pull может пропустить запись навсегда;
- commit с неопределённым исходом безопасен только благодаря журналу мутаций: серверный повтор транзакции — тоже повтор push;
- push одного пользователя сериализуются. Это корректно, но означает `503` при всплеске (≥ 20 одновременных) и требует backoff на клиенте.

### 5.3. Стоимость в RU: что измерено, а что нет

`x-ydb-consumed-units` — RU, которые возвращает сервер YDB на каждый RPC. Он перехватывается в gRPC-канале драйвера (`syncproto/metering.py`).
- **Чтения локальная YDB тарифицирует достоверно**: заголовок совпадает с формулой (pull 100 = 101 и 101).
- **Записи локальная YDB не тарифицирует**: push 1 и push 500 — по 2 RU, autocommit `UPSERT` 500 строк — 1 RU. Представление `.sys/top_queries_by_request_units_*` тоже не учитывает записи и добавляет CPU компиляции.

Поэтому для push показываются **фактические строки и байты из статистики YDB** (`stats_mode=BASIC`) и RU, посчитанные из них по [официальной формуле](https://yandex.cloud/ru/docs/ydb/pricing/ru-yql) `max(CPU/1,5 мс; чтения + 2 × записи)` [Ф]. Подтвердить их может только облако: в `cloud/measure.py` и `bench --target url` заголовок Serverless сравнивается с формулой.

## 8. Архитектурное заключение

**Подходит ли YDB Serverless?** Да. Каждая операция sync — это точечное чтение по PK или диапазон `(user_id, version > cursor)` с LIMIT. Стоимость не растёт с историей пользователя [И], транзакции надёжны [И], TTL работает [И]. Ограничения: дорогое хранение, сериализация push на пользователя, лимит RU/с по умолчанию — все решаются параметрами и политиками, а не сменой БД.

**Sync-модель:** вариант B (§2–3).

**HLC:** не нужен (§3.2).

**Риск потери данных:** при соблюдении правил клиента (§2) подтверждённые изменения не теряются, удаления окончательны, дублей нет [И]. Принятый риск — LWW по записи при конкурентных правках (§0).

**Что будет при 10–50k MAU:**
- код и протокол не меняются. Данные и нагрузка разбиты по `user_id` (PK и индекс начинаются с него), auto-partitioning по размеру и нагрузке включён;
- средняя нагрузка при 50k base ≈ 78 млн RU/мес ≈ 30 RU/с, в пиках в разы больше. Значит, лимит пропускной способности нужно поднять сразу: **значение по умолчанию 10 RU/с меньше одной первичной выгрузки (≈6 000 RU)** [Ф];
- конкурентность одного пользователя (1–3 устройства) далека от предела в ~16 одновременных push [И].

**Корректировки к architecture-local-first.md:**
1. §8.1–8.2: `updated_at (HLC)` → `baseVersion` в мутации, `order_ts` на сервере. Клиенту не нужно HLC-состояние.
2. §8.4 «удаление против редактирования — LWW» → **delete wins**, tombstone окончателен.
3. §8.2: в ответ `superseded` / `rejected` / повтор **всегда** прикладывать актуальную запись. `noop` — только при совпадении `mutationId`. Правка того же устройства всегда новее.
4. §8.1: индекс явно `GLOBAL SYNC`. Выбор COVER или без COVER — по горизонту хранения (§7). Pull — только snapshot или serializable чтение.
5. §8.2: при исчерпании повторов транзакции — `503` + `Retry-After`. Клиенту нужен backoff.
6. §2 и §7.4: хранение ~900 Б на запись (не 500). Политика хранения tombstones (уже в §8.4) и неактивных аккаунтов обязательна до запуска.
7. §7.4: лимит RU/с ≥ 100–300 с первого дня — не только как предохранитель, но и чтобы первичная синхронизация не троттлилась.
8. Журнал `sync_mutations` стоит треть RU push. Пока оставить: он даёт точный повтор ответа. Позже можно оценить идемпотентность по `mutation_id` в самой записи (−32 % RU push), но для этого нужны отдельные тесты.

| Гипотеза | Как проверить |
