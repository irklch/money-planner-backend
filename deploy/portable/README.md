# Переносимое развёртывание

Один Linux-сервер с Docker у любого провайдера: PostgreSQL 16, API, ежедневная очистка guest, резервные копии и Caddy с Let's Encrypt. Сервисы облачного провайдера не нужны: реестр образов, Lockbox, Managed PG, Cloud Logging и metadata-IAM заменены на сборку на сервере, `.env`, PostgreSQL в контейнере, `json-file` логи и API-ключ ИИ.

Аварийный план (переезд, переключение DNS, возврат) — [`docs/disaster-recovery.md`](../../docs/disaster-recovery.md). Старое развёртывание в Yandex Cloud — [`deploy/README.md`](../README.md).

```
Интернет ──443──► caddy ──► api ──► db (том pgdata, наружу не публикуется)
                            maintenance ┘   ▲
                            backup ─────────┘── pg_dump → age → rclone ──► S3 другого провайдера
```

## Требования к серверу

| Параметр | Минимум | Комментарий |
|---|---|---|
| ОС | Ubuntu 22.04/24.04 или Debian 12 | x86_64 или arm64 |
| CPU / RAM | 1 полное ядро / 2 ГБ + swap 1–2 ГБ | проверено на 2 vCPU × 50 % / 2 ГБ, см. «Минимальная конфигурация». В Yandex Compute меньше 2 vCPU не бывает |
| Диск | 20 ГБ | образы ≈ 1,5 ГБ, БД — мегабайты |
| Сеть | публичный IPv4, входящие 22, 80, 443 | 80 нужен Let's Encrypt |
| Исходящий доступ | Docker Hub, PyPI, Debian, S3 копий, Let's Encrypt | без них не соберутся образы |

## Параметры и секреты

Все значения — в `deploy/portable/.env` на сервере (шаблон [`env.example`](env.example), права `600`). В git, metadata ВМ и чаты значения не попадают.

| Переменная | Секрет | Откуда | Что будет при потере |
|---|---|---|---|
| `API_DOMAIN` | нет | домен API, A-запись на сервер | — |
| `FENCE_EXPECTED_IP` | нет | публичный IPv4 сервера | — |
| `FENCE_MODE` | нет | `enforce`; `off` только до переключения DNS | — |
| `INSTANCE_NAME` | нет | имя сервера в путях копий | — |
| `POSTGRES_PASSWORD` | да | `openssl rand -hex 32` (≥ 24 символов; `install.sh` отклоняет пробелы, `$`, кавычки, `\` и `#`). В URL подключения пароль кодирует приложение (`DB_*` → `app/core/config.py`), поэтому `/ + = @ : % ? &` допустимы | задаётся заново при восстановлении |
| `JWT_SECRET` | да | `openssl rand -hex 32` | access-токены (15 мин) станут недействительны; клиенты обновят их по refresh |
| `TOKEN_DERIVATION_SECRET` | да | `openssl rand -hex 32`, отличный от JWT | refresh-токены продолжат работать (в БД только SHA-256); повтор `POST /v1/auth/guest` в пределах 24 ч получит `409`, а повтор refresh в grace-окне — `401` (клиент создаст новую гостевую запись) |
| `AI_ENABLED`, `AI_FOLDER_ID`, `AI_API_KEY`, `AI_MODEL_*` | ключ — да | Yandex AI Studio, API-ключ сервисного аккаунта | `AI_ENABLED=false`: импорт работает, нераспознанные операции — «без категории» |
| `BACKUP_AGE_RECIPIENT` | нет (публичный ключ) | `age-keygen` на компьютере владельца | новые копии не снимаются |
| приватный ключ age | **да, критичный** | только у владельца, **не на сервере** | **все копии нельзя расшифровать** |
| `BACKUP_REMOTE`, `RCLONE_CONFIG_OFFSITE_*` | ключ доступа — да | бакет S3 у другого провайдера | копии остаются только на сервере |

Ни один секрет приложения не делает данные невосстановимыми: восстановлению нужен только приватный ключ age и доступ к бакету.

## Установка на чистый сервер

```bash
# 1. На компьютере владельца (один раз): ключ шифрования копий
age-keygen -o money-planner-backup.key      # приватный ключ → менеджер паролей + офлайн-копия
grep public money-planner-backup.key        # age1... → BACKUP_AGE_RECIPIENT

# 2. На сервере
git clone https://github.com/irklch/money-planner-backend.git /opt/money-planner
cd /opt/money-planner/deploy/portable
cp env.example .env && chmod 600 .env && nano .env
sudo ./install.sh
./smoke.sh                                   # healthz (готовность БД), гостевая сессия, refresh, отключённые маршруты
./smoke.sh "https://$API_DOMAIN"             # после выпуска сертификата
docker compose run --rm backup once          # первая копия и проверка доступа к бакету
docker compose run --rm backup list
```

Обновление: `git pull && sudo ./install.sh`. Миграции выполняет сервис `migrate` при каждом запуске.

Замечания по первому запуску (проверено на Ubuntu 24.04, 2 vCPU / 4 ГБ, 11.10.2026):
- запускайте `install.sh` в `tmux` или через `nohup`: включение ufw обрывает текущую SSH-сессию. Сам скрипт при этом продолжает работу, SSH остаётся разрешён;
- первая установка с Docker из apt и сборкой образов заняла ≈ 10 мин; пересборка без кэша — 134 с (замеры ниже). На сервере с 2 ГБ RAM добавьте swap как страховку: сборка — самый требовательный к памяти этап;
- Docker публикует порты в обход ufw. Поэтому API привязан к `127.0.0.1`, а порт БД не публикуется вообще.

### Тестовый стенд без домена

`sudo ./install.sh --test` с `FENCE_MODE=off` и пустым `COMPOSE_PROFILES` в `.env`. Caddy в профиле `public` и не запускается даже при `docker compose up -d`; наружу открыт только SSH, API слушает `127.0.0.1:8000`:

```bash
ssh -L 18000:127.0.0.1:8000 <user>@<ip>      # API на http://127.0.0.1:18000 у разработчика
```

Тестовый стенд — только для синтетических данных: без домена, TLS и внешних копий он не production.

## Минимальная конфигурация

Замеры 13.10.2026 на тестовом стенде: Yandex Compute standard-v3 (Ice Lake), **2 vCPU с гарантированной долей 50 % / 2 ГБ RAM**, network-ssd 30 ГБ, swap-файл 2 ГБ (`vm.swappiness=10`), один процесс uvicorn, параметры приложения по умолчанию. **Данные синтетические, AI выключен (`AI_ENABLED=false`).** Это краткий замер на разделяемом vCPU, а не гарантия постоянной производительности: соседи по хосту, рост БД, включённый AI и реальные выписки изменят цифры. Перед production замер повторяется на выбранной ВМ (E12).

Swap:

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
echo "/swapfile none swap sw 0 0" | sudo tee -a /etc/fstab
echo "vm.swappiness=10" | sudo tee /etc/sysctl.d/99-money-planner-swap.conf && sudo sysctl -p /etc/sysctl.d/99-money-planner-swap.conf
```

> **Замеры ниже сделаны 13.10.2026 до E1** (сохранение импорта через `/v1/expenses/import` и аналитика тогда работали на сервере). С E1 `loadtest.py` измеряет разбор выписок и `/healthz`; после обновления стенда замер нужно повторить.

Повтор замеров: `scripts/make_synthetic_statement.py 40 big.xlsx` (≈ 4 800 расходов, 267 КБ), затем на сервере `python3 deploy/portable/loadtest.py tests/fixtures/banks/alfa/alfa_statement_test.xlsx big.xlsx`.

¹ Без страничного кэша; доступно 1 966 МБ. Перезапусков контейнеров и OOM — 0 во всех сценариях.
² При 8 одновременных разборах 4 сверх `PARSE_CONCURRENCY_GLOBAL=4` получают `429` с `Retry-After: 5` и повторяют; суммарное ожидание — 20 с на 8 запросов.

Сравнение с 2 vCPU × 100 % / 4 ГБ (11.10.2026): смешанные запросы — 154 → 167 запросов/с, p95 82 → 76 мс (в пределах разброса); простой — ≈ 120 МБ на контейнеры в обоих случаях.

**Вывод:** для MVP хватает с большим запасом: проверенная нагрузка — 8 одновременных импортов по 4 800 операций и ≈ 160 запросов/с. Память используется меньше чем на треть, swap не понадобился. Узкое место при всплеске импортов — CPU одного процесса uvicorn, а при сборке — диск, не память.

**Рекомендуемые параметры:** один процесс uvicorn (rate limit и семафор разбора хранятся в памяти процесса — с несколькими процессами лимиты умножаются); `PARSE_CONCURRENCY_GLOBAL=4` (по умолчанию) — достаточно для 1 ядра, при 2 ГБ без swap не повышать; `PARSE_CONCURRENCY_PER_USER=1`; `DB_POOL_SIZE=10`, `DB_MAX_OVERFLOW=5` — пик 8 одновременных сохранений укладывается.

### Обновление стенда после E1

Схема MVP приходит миграцией `0004_mvp_schema`; сброс БД не нужен. Сервис `migrate` применит её при запуске:

```bash
cd /opt/money-planner && git pull                     # ветка main после слияния E1
cd deploy/portable
docker compose run --rm backup once                   # копия до миграции (тестовый ключ стенда)
sudo ./install.sh --test                              # сборка образов, migrate 0003 → 0004, перезапуск
docker compose exec -T db psql -U money -d money -Atc "select version_num from alembic_version"   # 0004_mvp_schema
./smoke.sh
```

Старые данные стенда сохраняются в `legacy_users`, `legacy_refresh_tokens` и старых таблицах. Откат: `docker compose run --rm --entrypoint python migrate -m alembic downgrade 0003_expense_imports_result`, затем код предыдущей версии.

### Обновление стенда после E2

Миграции нет (таблицы `devices` и `refresh_tokens` созданы в E1, ревизия остаётся `0004_mvp_schema`), сброс БД не нужен:

```bash
cd /opt/money-planner && git pull                     # ветка main после слияния E2
cd deploy/portable
docker compose run --rm backup once                   # копия до обновления
sudo ./install.sh --test                              # сборка образов, migrate (без изменений), перезапуск api
docker compose exec -T db psql -U money -d money -Atc "select version_num from alembic_version"   # 0004_mvp_schema
./smoke.sh                                            # /v1/auth/guest, повтор, ротация, grace, токен принят, 404
```

После обновления сессии старого `/v1/auth/anonymous` недействительны (`401 refresh_token_invalid`, access — `401 access_token_invalid`): клиент создаёт гостевую запись через `/v1/auth/guest`. Данные `legacy_*` не трогаются (удаление — E11). Откат: код предыдущей версии и `install.sh --test`; созданные E2 строки `devices` и `refresh_tokens` старый код не читает. `loadtest.py` после обновления создаёт сессии через `/v1/auth/guest`.

## Резервные копии

- **Что копируется:** вся БД `money` (`pg_dump -Fc`). Других постоянных данных у сервера нет: выписки не сохраняются, сертификаты Caddy выпускаются заново.
- **Когда:** каждые `BACKUP_INTERVAL_HOURS` (6) и вручную `docker compose run --rm backup once`.
- **Где:** том `backups` на сервере (`BACKUP_KEEP_LOCAL_DAYS`, 3 дня) и `BACKUP_REMOTE/<INSTANCE_NAME>/` (`BACKUP_KEEP_REMOTE_DAYS`, 35 дней).
- **Защита:** файлы шифруются age на публичный ключ, рядом лежат `.sha256` и `.manifest.json` (ревизия миграций и число строк по таблицам, без данных). Сервер не может расшифровать копии, поэтому его взлом не раскрывает историю.
- **Хранилище:** S3 другого провайдера, не того, где работает сервер. Ключ — только к этому бакету; если провайдер позволяет — версионирование или блокировка удаления, чтобы взломанный сервер не стёр копии.
- **Контроль:** healthcheck сервиса `backup` становится `unhealthy`, если успешной копии нет дольше 2 интервалов (`docker compose ps`).
- **Проверка домена:** перед каждой копией проверяется, что `API_DOMAIN` указывает на этот сервер (как `fence_check` у API), чтобы старая ВМ после переезда не выкладывала копии устаревшей БД. Это дополнительная проверка, а не гарантия: при ошибке DNS копия снимается.

### Восстановление

Порядок: **пустая БД → восстановление → миграции → приложение** (подробно — [`docs/disaster-recovery.md`](../../docs/disaster-recovery.md) §2–§3):

```bash
sudo ./install.sh --prepare          # Docker, проверки, образы и только пустая БД; без migrate, api, backup, caddy
# приватный ключ — временно, на время восстановления, затем удалить
docker compose run --rm -v /root/age.key:/run/age.key:ro backup restore latest   # или имя money-YYYYmmddTHHMMSSZ
shred -u /root/age.key
sudo ./install.sh                    # migrate догоняет схему до текущей ревизии, затем стартуют сервисы
./smoke.sh
```

`restore` проверяет `sha256`, отказывается писать в непустую БД (кроме `RESTORE_FORCE=yes`) и сверяет число строк с манифестом. Копия может быть старее текущей схемы: она восстанавливается со своей ревизией Alembic, `migrate` доводит её до текущей.

### Учения

`./drill.sh` — учения в изолированном compose-проекте на синтетических данных. Запускается в CI (job `portable-deploy`) и вручную на любой машине с Docker. Пароль БД в учениях содержит `/ + = @ : % ? & ~`.

1. **Копия старой версии схемы, по шагам аварийного плана:** сервер → синтетические данные старой схемы (`legacy_*`; старого входа через API с E2 нет) → откат схемы на предыдущую ревизию (как на стенде до E1) → зашифрованная копия → уничтожение сервера с томами → только пустая БД → восстановление → миграции до текущей ревизии и приложение → данные старой схемы совпадают, старая сессия получает `401 refresh_token_invalid` (с E2 действуют только сессии `/v1/auth/guest`), `smoke.sh` проходит.
2. **Текущая схема, со сквозной сессией API (E2):** гостевая запись устройства и ротация refresh через `/v1/auth/guest` и `/v1/auth/refresh`, синтетические строки остальных таблиц MVP (через API они пишутся с E5/E6) → копия → уничтожение сервера с томами → пустая БД → восстановление → совпадение числа строк и md5 таблиц MVP; сессия до аварии продолжает работать, повтор ключа установки → `409`, `smoke.sh` проходит.

## Один пишущий сервер

Единственность пишущего сервера обеспечивает порядок действий: **перед переключением DNS запись на старом сервере подтверждённо останавливается** ([`docs/disaster-recovery.md`](../../docs/disaster-recovery.md) §5). Если подтвердить это нельзя, переключение — осознанный риск потерь и расхождения данных.

`app/jobs/fence_check.py` — дополнительная проверка при старте `migrate`, `api` и `maintenance`: если A-запись `API_DOMAIN` указывает не на `FENCE_EXPECTED_IP`, контейнер не запускается. Она **не гарантирует** единственного пишущего сервера: уже работающий API после смены DNS не останавливается, при ошибке DNS запуск разрешается, клиенты со старым кэшем DNS или по IP продолжают обращаться к старому серверу.
