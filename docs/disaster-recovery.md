# Аварийный план: перенос backend к другому провайдеру

Редакция 11.10.2026. Относится к текущему коду (FastAPI + PostgreSQL) и развёртыванию [`deploy/portable`](../deploy/portable/README.md). Состояние инфраструктуры на дату редакции — [`infra-audit-2026-10-11.md`](infra-audit-2026-10-11.md).

Принцип: **основной сервер — тот, на который указывает A-запись домена API.** Переключение — это смена A-записи. Данные переносятся только через зашифрованные копии во внешнем хранилище. Консоль и API старого провайдера для восстановления не нужны.

## 0. Что должно быть готово заранее

Без этих пунктов восстановление без доступа к Yandex Cloud невозможно.

| # | Что | Где хранится | Проверка |
|---|---|---|---|
| 1 | Домен API, DNS **не у основного провайдера** (регистратор или отдельный DNS-хостинг), TTL A-записи 300 с | у регистратора | `dig +short A <домен>`; TTL ≤ 300 |
| 2 | iOS-приложение обращается **только по домену**, без IP и без адресов облака (`*.yandexcloud.net`, `*.apigw.yandexcloud.net`) | код iOS | поиск по проекту iOS |
| 3 | Приватный ключ age | менеджер паролей + офлайн-копия | расшифровка тестового файла раз в квартал |
| 4 | Бакет S3 у **второго** провайдера и ключ доступа к нему | менеджер паролей | `docker compose run --rm backup list` |
| 5 | Копия `.env` действующего сервера | менеджер паролей | — |
| 6 | Аккаунт и способ оплаты у резервного провайдера, квота на 1 ВМ | у провайдера | вход в панель |
| 7 | Доступ к GitHub-репозиторию (код и инструкция) | — | `git clone` |
| 8 | Учения `deploy/portable/drill.sh` прошли за последние 3 месяца | CI / журнал | зелёный job `portable-deploy` |

## 1. Решение о переезде

Переезжать, если выполнено хотя бы одно:
- API недоступен дольше 30 минут, а провайдер не называет срок восстановления;
- провайдер официально рекомендует переносить нагрузку (как Yandex Cloud 08–11.10.2026);
- зона или площадка сервера остановлена.

Недоступность из одной сети ещё не отказ. Проверьте с двух независимых сетей (мобильный интернет и внешний чекер), а также статус провайдера.

## 2. Развернуть новый сервер (≈ 30–60 мин, оценка)

1. Создать ВМ у резервного провайдера: Ubuntu 24.04, 2 vCPU / 2 ГБ / 20+ ГБ, публичный IPv4, SSH-ключ. Записать IP.
2. Взять из менеджера паролей копию `.env` и изменить в ней:
   - `FENCE_EXPECTED_IP` — IP нового сервера;
   - `FENCE_MODE=off` — до переключения DNS домен ещё указывает на старый сервер;
   - `INSTANCE_NAME` — новое имя (`mp-<провайдер>-<n>`), чтобы копии нового сервера лежали отдельно от старых;
   - `AI_ENABLED=false`, если AI Studio недоступен (иначе разбор выписок с нераспознанными операциями вернёт `500`).
   
   Если `.env` потерян, сгенерировать секреты заново (`deploy/portable/README.md`, таблица параметров): пользователи не разлогинятся.
3. Установить без запуска API:
   ```bash
   git clone https://github.com/irklch/money-planner-backend.git /opt/money-planner
   cd /opt/money-planner/deploy/portable && nano .env && chmod 600 .env
   sudo ./install.sh && docker compose stop api maintenance backup
   ```

## 3. Восстановить данные (≈ 5–15 мин, оценка; измерено 76 с на тестовой БД)

```bash
# Копии старого сервера: INSTANCE_NAME старого сервера
docker compose run --rm -e INSTANCE_NAME=<старое имя> backup list
# приватный ключ age — временно
docker compose run --rm -e INSTANCE_NAME=<старое имя> -v /root/age.key:/run/age.key:ro backup restore latest
shred -u /root/age.key
docker compose up -d
```

`restore` проверяет контрольную сумму, расшифровывает, восстанавливает и сверяет число строк с манифестом. Миграции догоняет `migrate`.

**Потеря данных (RPO):** всё, что записано после последней копии во внешнем хранилище, — до `BACKUP_INTERVAL_HOURS` (6 ч). Если старый сервер ещё отвечает, сначала снять свежую копию на нём: `docker compose stop api && docker compose run --rm backup once`. Тогда потерь нет.

## 4. Проверить новый сервер до переключения

DNS ещё указывает на старый сервер, поэтому сертификат для домена не выпустится. Проверяем по HTTP на самом сервере и по IP:

```bash
./smoke.sh                                   # на сервере: healthz, запись и чтение БД
curl -sS http://<новый IP>/ -o /dev/null -w '%{http_code}\n'   # снаружи: порт открыт (Caddy ответит редиректом)
docker compose ps                            # все сервисы healthy, migrate завершился с 0
docker compose logs --tail 50 api            # нет ошибок старта
```

Сверить с манифестом копии (вывод `restore`): число `users`, `expenses`, `categories`.

## 5. Исключить запись в две БД

Опасный сценарий: после переезда старая ВМ снова включается, её контейнеры (`restart: always`) стартуют и принимают запросы от клиентов с закэшированным DNS или по IP.

Защита — три уровня:

1. **Fencing по DNS** (`app/jobs/fence_check.py`, `backup.sh`). На каждом старте `api`, `migrate`, `maintenance` и перед каждой копией сервер сверяет A-запись домена со своим `FENCE_EXPECTED_IP`. Старый сервер после переключения увидит чужой IP и **не запустится**, а также не выложит копии. Если DNS не отвечает, сервер стартует: иначе сбой DNS уронил бы единственный сервер.
2. **Порядок переключения.** Сначала остановить запись на старом (если доступен), затем перенести данные, затем переключить DNS:
   ```bash
   # старый сервер, если доступен
   docker compose stop api maintenance && docker compose run --rm backup once && docker compose stop backup
   ```
3. **Старый сервер выключен у провайдера** — как только станет доступна консоль. Удалять — только после стабилизации нового и отдельного решения.

После переключения DNS ещё до TTL (5 мин) часть клиентов может обращаться к старому адресу. Если старый сервер в это время работает, его записи пропадут. Поэтому шаг 2 выполняется до шага 6.

Ограничение: `fence_check` срабатывает при старте контейнера. Если старый сервер **не перезагружался** и продолжает работать после смены DNS, он будет принимать запросы клиентов со старым кэшем DNS до остановки. Поэтому шаг 2 обязателен, а при его невозможности переключение делается с осознанным риском и последующей ручной сверкой (раздел 8).

## 6. Переключить API через домен (≈ 5 мин + TTL)

iOS-приложение обновлять не нужно: оно ходит на домен.

1. У регистратора / DNS-хостинга заменить A-запись `API_DOMAIN` на IP нового сервера (TTL 300). AAAA-запись удалить или тоже заменить.
2. Дождаться: `dig +short A <домен> @1.1.1.1` и `@8.8.8.8` возвращают новый IP.
3. На новом сервере `FENCE_MODE=enforce` в `.env` и `docker compose up -d` (контейнеры пересоздадутся). Caddy выпустит сертификат автоматически.
4. Проверка снаружи: `./smoke.sh https://<домен>`; затем вход в iOS-приложение на реальном устройстве.

## 7. После переключения

- `docker compose run --rm backup once` — первая копия с новым `INSTANCE_NAME`.
- Убедиться, что `backup` healthy через 6 ч.
- Обновить копию `.env` в менеджере паролей.
- Записать в журнал: время решения, время переключения, имя последней восстановленной копии.

## 8. Возврат на прежний сервер без потери новых данных

Возврат — это такой же переезд, только в обратную сторону. Старая БД **не используется** как источник: в ней нет данных, записанных после переезда.

1. Старый сервер: убедиться, что `api` не запущен (fencing его остановил). Снять архивную копию его БД — на случай, если в ней есть записи, не попавшие в последнюю копию перед переездом:
   ```bash
   docker compose run --rm -e FENCE_MODE=off -e INSTANCE_NAME=<старое имя>-archive backup once
   ```
2. Новый сервер: `docker compose stop api maintenance && docker compose run --rm backup once`.
3. Старый сервер: очистить БД и восстановить из копии нового сервера:
   ```bash
   docker compose run --rm -e INSTANCE_NAME=<имя нового> -e RESTORE_FORCE=yes \
     -v /root/age.key:/run/age.key:ro backup restore latest
   ```
4. Проверки раздела 4, затем переключение DNS (раздел 6) с `FENCE_EXPECTED_IP` старого сервера.
5. Записи из архивной копии старого сервера (шаг 1), не вошедшие в копию перед переездом, сверяются вручную по `created_at`/`updated_at`. Автоматического слияния нет. Для текущего кода это расходы и категории пользователей; в local-first архитектуре источник истины — устройство, и такие записи восстановит повторная синхронизация клиента.

| Смена DNS | — | TTL 300 с → ~5–10 мин |
| **Итого RTO** | — | **≈ 1–2 ч** при готовых пунктах раздела 0; **4–8 ч и больше**, если аккаунт, домен или ключи готовятся в момент аварии |
