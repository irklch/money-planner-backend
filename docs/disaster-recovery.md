# Аварийный план: перенос backend к другому провайдеру

Редакция 13.10.2026. Относится к текущему коду (FastAPI + PostgreSQL) и развёртыванию [`deploy/portable`](../deploy/portable/README.md). Состояние инфраструктуры — [`infra-audit-2026-10-11.md`](infra-audit-2026-10-11.md).

Принципы:
- **Клиенты попадают на сервер, на который указывает A-запись домена API.** Переключение — это смена A-записи, iOS-приложение не обновляется.
- **Данные переносятся только через зашифрованные копии** во внешнем хранилище. Консоль и API старого провайдера для восстановления не нужны.
- **Писать должен только один сервер. Это обеспечивает порядок действий, а не автоматика:** переключение безопасно, только если запись на старом сервере **подтверждённо остановлена** (раздел 5). `fence_check` — дополнительная проверка при старте, а не гарантия.

## 0. Что должно быть готово заранее

Без этих пунктов восстановление без доступа к Yandex Cloud невозможно.

| # | Что | Где хранится | Проверка |
|---|---|---|---|
| 1 | Домен API, DNS **не у основного провайдера** (регистратор или отдельный DNS-хостинг), TTL A-записи 300 с | у регистратора | `dig +short A <домен>`; TTL ≤ 300 |
| 2 | iOS-приложение обращается **только по домену**, без IP и без адресов облака (`*.yandexcloud.net`, `*.apigw.yandexcloud.net`) | код iOS | поиск по проекту iOS |
| 3 | Приватный ключ age | менеджер паролей + офлайн-копия | расшифровка тестового файла раз в квартал |
| 4 | Бакет S3 у **второго** провайдера и ключ доступа к нему | менеджер паролей | `docker compose run --rm backup list` |
| 5 | Копия `.env` действующего сервера | менеджер паролей | — |
| 6 | Аккаунт и способ оплаты у резервного провайдера, квота на 1 ВМ | у провайдера | вход в панель |
| 7 | Доступ к GitHub-репозиторию (код и инструкция) | — | `git clone` |
| 8 | Учения `deploy/portable/drill.sh` прошли за последние 3 месяца | CI / журнал | зелёный job `portable-deploy` |

## 1. Решение о переезде

Переезжать, если выполнено хотя бы одно:
- API недоступен дольше 30 минут, а провайдер не называет срок восстановления;
- провайдер официально рекомендует переносить нагрузку (как Yandex Cloud 08–11.10.2026);
- зона или площадка сервера остановлена.

Недоступность из одной сети ещё не отказ. Проверьте с двух независимых сетей (мобильный интернет и внешний чекер), а также статус провайдера.

**Сразу же выясните, можно ли остановить запись на старом сервере** (раздел 5): от этого зависит, будет ли переезд без потерь.

## 2. Подготовить новый сервер (≈ 30–60 мин, оценка)

1. Создать ВМ у резервного провайдера: Ubuntu 24.04, 1–2 vCPU / 2 ГБ / 20+ ГБ, публичный IPv4, SSH-ключ. Записать IP.
2. Взять из менеджера паролей копию `.env` и изменить в ней:
   - `FENCE_EXPECTED_IP` — IP нового сервера;
   - `FENCE_MODE=off` — до переключения DNS домен ещё указывает на старый сервер;
   - `INSTANCE_NAME` — новое имя (`mp-<провайдер>-<n>`), чтобы копии нового сервера лежали отдельно от старых;
   - `AI_ENABLED=false`, если AI Studio недоступен (иначе разбор выписок с нераспознанными операциями вернёт `500`).

   Если `.env` потерян, сгенерировать секреты заново (`deploy/portable/README.md`, таблица параметров): пользователи не разлогинятся.
3. Установить **только пустую БД**: без миграций, API, фоновых задач, копий и Caddy.
   ```bash
   git clone https://github.com/irklch/money-planner-backend.git /opt/money-planner
   cd /opt/money-planner/deploy/portable && nano .env && chmod 600 .env
   sudo ./install.sh --prepare
   ```
   `--prepare` ставит Docker, проверяет `.env`, собирает образы и запускает только `db`. Если приложение на сервере уже работает, скрипт откажется; если в БД уже есть таблицы, предупредит.

## 3. Восстановить данные (≈ 5–15 мин, оценка; измерено ≈ 2 мин на тестовой БД)

Порядок: **пустая БД → восстановление копии → миграции → приложение.**

```bash
# 1. Найти копию старого сервера (INSTANCE_NAME старого сервера)
docker compose run --rm -e INSTANCE_NAME=<старое имя> backup list
# 2. Восстановить в пустую БД; приватный ключ age — временно
docker compose run --rm -e INSTANCE_NAME=<старое имя> -v /root/age.key:/run/age.key:ro backup restore latest
shred -u /root/age.key
# 3. Миграции до текущей версии схемы и запуск приложения
sudo ./install.sh
```

- `restore` проверяет контрольную сумму, расшифровывает, восстанавливает и сверяет число строк с манифестом. В непустую БД он не пишет (кроме `RESTORE_FORCE=yes`).
- Копия может быть **старее текущей схемы**: она восстанавливается со своей ревизией Alembic, а сервис `migrate` при `install.sh` догоняет схему до текущей. Сценарий проверяется в CI: `drill.sh` откатывает схему на предыдущую ревизию, снимает копию и восстанавливает её этими же шагами.
- Копия **новее кода** (сервер откатили на старый коммит) не поддерживается: сначала обновите код до версии, с которой копия снята.

**Потеря данных (RPO):** всё, что записано на старом сервере после последней копии во внешнем хранилище, — до `BACKUP_INTERVAL_HOURS` (6 ч). Если запись на старом сервере подтверждённо остановлена и после этого снята копия (раздел 5, вариант А), потерь нет.

## 4. Проверить новый сервер до переключения

DNS ещё указывает на старый сервер, поэтому сертификат для домена не выпустится. Проверяем на самом сервере и по IP:

```bash
./smoke.sh                                   # на сервере: healthz, запись и чтение БД
curl -sS http://<новый IP>/ -o /dev/null -w '%{http_code}\n'   # снаружи: порт открыт (ответит Caddy)
docker compose ps                            # все сервисы healthy, migrate завершился с 0
docker compose logs --tail 50 api            # нет ошибок старта
```

Сверить с манифестом копии (вывод `restore`) число `users`, `expenses`, `categories`.

## 5. Один пишущий сервер

**Условие безопасного переключения: запись на старом сервере подтверждённо остановлена до смены DNS.** Без этого нельзя обещать отсутствие потерь.

Подтверждением считается одно из:

| Вариант | Как подтвердить |
|---|---|
| А. Старый сервер доступен по SSH | `docker compose stop api maintenance`, затем `docker compose run --rm backup once` — копия снимается **после** остановки, затем `docker compose stop backup`. Проверить, что `docker compose ps --status running` не показывает `api`, `maintenance`, `migrate`. Восстанавливать именно эту копию |
| Б. Доступна консоль или API провайдера | ВМ в статусе «остановлена» и не запустится сама (нет автоперезапуска и расписаний) |
| В. Провайдер подтвердил, что ВМ или площадка выключены | официальное сообщение со сроками; сохранить ссылку в журнал |

**Если подтвердить остановку нельзя** (сервер и консоль недоступны, статуса нет), переключение — осознанный риск. Его принимает владелец:
- старый сервер может работать для части клиентов: с закэшированным DNS, по IP или после восстановления площадки;
- записи, сделанные на нём после последней внешней копии, **не попадут на новый сервер**. Часть из них может быть потеряна или потребует ручной сверки;
- новый и старый серверы расходятся до тех пор, пока старый не остановлен.

Что делать в этом случае: переключаться только по решению владельца, записать время последней восстановленной копии, а как только старый сервер станет доступен — **сразу остановить на нём запись** и снять архивную копию (раздел 8, шаг 1). Затем сверить записи вручную. Для текущего кода это расходы и категории. В local-first архитектуре источник истины — устройство: записи, отклонённые или потерянные сервером, клиент отправит повторно при синхронизации, но обещать это без реализации E6 нельзя.

### Что делает и чего не делает `fence_check`

`app/jobs/fence_check.py` (и аналог в `backup.sh`) при **старте** `migrate`, `api`, `maintenance` и перед каждой копией сравнивает A-запись домена с `FENCE_EXPECTED_IP`. Если домен указывает на другой IP, запуск или копия отменяются.

Это снижает риск, но **не гарантирует единственного пишущего сервера**:
- уже работающий API не останавливается после смены DNS — проверка только при старте;
- при ошибке DNS запуск разрешается (иначе сбой DNS уронил бы единственный сервер);
- резолвер сервера может вернуть закэшированный старый ответ до истечения TTL;
- клиенты со старым кэшем DNS или по IP продолжают обращаться к старому серверу, пока он работает;
- `FENCE_MODE=off` отключает проверку полностью.

Поэтому `fence_check` не заменяет подтверждённую остановку записи. Сложное автоматическое переключение и арбитр (lease, кворум) в MVP не делаются.

## 6. Переключить API через домен (≈ 5 мин + TTL)

Только после раздела 5 (подтверждённая остановка записи или принятый риск).

1. У регистратора / DNS-хостинга заменить A-запись `API_DOMAIN` на IP нового сервера (TTL 300). AAAA-запись удалить или тоже заменить.
2. Дождаться, пока `dig +short A <домен> @1.1.1.1` и `@8.8.8.8` вернут новый IP.
3. На новом сервере `FENCE_MODE=enforce` в `.env` и `sudo ./install.sh` (контейнеры пересоздадутся). Caddy выпустит сертификат автоматически.
4. Проверка снаружи: `./smoke.sh https://<домен>`; затем вход в iOS-приложение на реальном устройстве.

## 7. После переключения

- `docker compose run --rm backup once` — первая копия с новым `INSTANCE_NAME`.
- Убедиться, что `backup` healthy через 6 ч.
- Обновить копию `.env` в менеджере паролей.
- Записать в журнал: время решения, способ подтверждения остановки (А/Б/В или принятый риск), время переключения, имя восстановленной копии.

## 8. Возврат на прежний сервер

Возврат — такой же переезд в обратную сторону: старая БД **не используется** как источник, в ней нет данных, записанных после переезда.

1. **Старый сервер: остановить запись и сохранить его БД** — в ней могут быть записи, не попавшие в копию перед переездом:
   ```bash
   docker compose stop api maintenance
   docker compose run --rm -e FENCE_MODE=off -e INSTANCE_NAME=<старое имя>-archive backup once
   docker compose run --rm -e INSTANCE_NAME=<старое имя>-archive backup list   # копия есть во внешнем хранилище
   ```
2. **Новый сервер: подтверждённо остановить запись** (раздел 5, вариант А) и снять копию:
   ```bash
   docker compose stop api maintenance && docker compose run --rm backup once && docker compose stop backup
   ```
3. **Старый сервер: пустая БД → восстановление → миграции → приложение.** Том БД удаляется, только когда архивная копия шага 1 видна во внешнем хранилище:
   ```bash
   docker compose down
   docker volume rm portable_pgdata          # имя тома: docker volume ls | grep pgdata
   sudo ./install.sh --prepare
   docker compose run --rm -e INSTANCE_NAME=<имя нового> -v /root/age.key:/run/age.key:ro backup restore latest
   shred -u /root/age.key
   ```
4. Проверки раздела 4, затем переключение DNS (раздел 6) с `FENCE_EXPECTED_IP` старого сервера и `sudo ./install.sh`.
5. Записи из архивной копии шага 1, которых нет в восстановленной БД, сверяются вручную по `created_at` / `updated_at`. Автоматического слияния нет.
