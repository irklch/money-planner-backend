## 0. Итог на одной странице

**Состав MVP** (план §0, §15):
- гостевой режим — финансовые данные только на устройстве;
- Sign in with Apple с бесплатной облачной синхронизацией `Expense`, `Category`, `DayMark`;
- импорт выписок гостю и аккаунту: 3 бесплатных подтверждённых импорта **учитываются, но исчерпание лимита импорт не блокирует** (`ENFORCE_QUOTAS=false`);
- **9 видов алгоритмической аналитики на iOS** — локально, бесплатно, без AI и без интернета; реализация обязана проходить Python-эталон и тест-векторы A1 (план §7);
- **AI — только категоризация операций при импорте**, которые не распознали правила сервера и подсказки клиента. Есть выключатель `AI_CATEGORIZATION_ENABLED`.

**После MVP:**
- AI-инсайты;
- Premium, оплата (StoreKit, App Store, российский эквайринг) и ограничения платного доступа;
- автоматическое удаление неактивных Apple-аккаунтов.

Через 12 месяцев очищаются только гостевые технические записи устройств: в них нет пользовательских данных.

**Стек — одна ВМ у провайдера с площадкой в РФ, без сервисов конкретного облака (решение D24, 13.10.2026):**

```
iOS (local-first) ──HTTPS──► домен API (DNS вне провайдера сервера)
                              │
                     ВМ: Docker Compose
                       Caddy (TLS Let's Encrypt) ─► FastAPI (1 процесс: auth, sync, импорт и учёт, удаление аккаунта)
                                                    ─► PostgreSQL 16 (том на диске ВМ, наружу не публикуется)
                       maintenance (фоновые задачи), backup (pg_dump → age → S3 другого провайдера)
                              │
                     AI Studio по API-ключу — только категоризация нераспознанных операций (выключатель)
```

| | Сейчас (тестовый стенд) | Production MVP |
|---|---|---|
| Сервер | существующая ВМ Yandex Cloud, 2 vCPU × 50 % / 2 ГБ, swap 2 ГБ, ≈ 2 175 ₽/мес | ВМ 1–2 vCPU / 2 ГБ у выбранного провайдера, ≈ 2 200–3 000 ₽/мес (план §13) |
| Резервные копии | тестовый ключ, только на ВМ | зашифрованные копии каждые 6 ч в S3 другого провайдера, < 100 ₽/мес |
| Готовность | синтетические данные, API только через SSH-туннель | после домена, HTTPS, внешних копий и проверки восстановления (план §11.3) |

AI-категоризация импорта — ожидаемо 5–10 / 25–50 / 250–500 ₽/мес при 20 / 100 / 1 000 пользователей (план §13.2). Аналитика на устройстве ничего не стоит.

**Почему так:**

1. **Local-first меняет нагрузку на backend.** Сервер не участвует в каждом действии: он нужен для фоновой синхронизации, входа, разбора выписок и удаления аккаунта. Нагрузка MVP — доли запроса в секунду; одна ВМ 1–2 vCPU / 2 ГБ справляется с запасом (замеры — план §11.3).
2. **Переносимость важнее экономии на нуле пользователей.** Инциденты Yandex Cloud 08–11.10.2026 показали: serverless-стек одного облака (API Gateway, Serverless Containers, YDB, Lockbox, KMS) не переносится к другому провайдеру без переписывания, а его резервные копии остаются внутри того же облака. Docker Compose + PostgreSQL переносятся на любую ВМ скриптом за ≈ 1–2 ч (`docs/disaster-recovery.md`).
3. **PostgreSQL подходит модели данных:** записи по `user_id` с журналом версий, устройства, аккаунты, учёт импортов (§3). Транзакция «пачка + счётчик версии пользователя», диапазонное чтение по версии и очистка по сроку решаются штатно; сериализация push одного пользователя — блокировкой строки счётчика или advisory-локом.
4. **Большая часть текущего кода удаляется или переносится на iPhone:** CRUD расходов и категорий, календарь, аналитика, insights. Парсер выписок, маскирование ПДн, AI-клиент, логика refresh-токенов, SQLAlchemy и Alembic остаются (§12).

**Цена решения:** фиксированные ≈ 2 200–3 000 ₽/мес вместо ≈ 25–60 ₽ при 20 пользователях у serverless-варианта, ручное администрирование одной ВМ и ответственность за резервные копии. Холодных стартов нет.

**Ответ на главный вопрос:** продуктовая логика, контракт E0 и модель sync не меняются. Меняется хранилище (PostgreSQL вместо YDB) и инфраструктура (ВМ + Compose вместо serverless Yandex). При росте до 10k+ MAU — вертикальное масштабирование ВМ, затем Managed PostgreSQL у того же провайдера (§7.5).

## 2. Нагрузочная модель

> Исследование 07.10.2026. Строки про Premium и insights относились к исходному составу; в MVP insights нет, импорт бесплатен (3 подтверждённых учитываются без блокировки). Актуальные допущения — план §13.

Консервативно считаю, что **у всех MAU есть аккаунт**. Гость нагружает backend только разбором выписок.

| На MAU в месяц | Base | Heavy |
|---|---:|---:|
| `sync/pull` (на открытие приложения) | 20 | 60 |
| `sync/push` (пачки изменений, ~8 записей) | 15 | 45 |
| `auth/refresh` | 20 | 60 |
| `me` | 5 | 15 |
| **Итого обычных запросов** | **60** | **180** |
| Импорт выписки (гость и аккаунт) | 1 | 3 |
| YDB, RU (оценка) | ~2 300 | ~4 900 |

**Допущения:**

- Стоимость запросов в YDB (RU) я оценил вручную по [формуле тарификации YQL](https://yandex.cloud/ru/docs/ydb/pricing/ru-yql): чтение — 1 RU за запись или блок 4 КБ, запись — 2 RU за запись или 1 КБ, CPU — 1 RU за 1,5 мс. Получилось ~6 RU на pull, ~63 RU на push из 8 записей с обновлением индекса, ~8 RU на refresh. Сверху ~1 000 RU в месяц на первичную загрузку истории новых аккаунтов. Точность ±2×, уточнить на прототипе по статистике запросов.
- Объём данных: ~120 записей в месяц на аккаунт × ~500 Б с индексом ≈ **0,75 МБ на аккаунт в год**. Через год: 10k — 7,5 ГБ, 50k — 37,5 ГБ. Через 3 года: 22,5 ГБ и 112 ГБ.
- Время работы контейнера: обычный запрос — 0,1 с (минимальная единица тарификации), разбор выписки — 5 с. Холодные старты — 20 / 5 / 1 / 0,5 с на MAU для 100 / 1k / 10k / 50k.
- Средний файл выписки — 50 КБ (см. предыдущее исследование).
- Исходящий трафик: ~5 КБ на ответ → 50k × 60 × 5 КБ ≈ 15 ГБ/мес. Это меньше бесплатных 100 ГБ у Yandex → **0 ₽ во всех вариантах Yandex**.
- Логи: ~1,2 ГБ/мес при 50k. Бесплатно 5 ГБ записи и 1 ГБ хранения → **0 ₽**.

## 3. Нужен ли PostgreSQL?

### Что сервер теперь хранит и как читает

| Данные | Доступ |
|---|---|
| Синхронизируемые записи (расходы, категории, отметки «День без расходов»; настройки не синхронизируются) | По ключу `(user_id, тип, id)` и диапазон `(user_id, version > cursor)` |
| Устройства (гостевые технические записи), аккаунты и identities (Apple `sub`) | По ключу |
| Refresh-токены | По хэшу токена |
| Учёт импортов (реестр, счётчики, доставки), лимиты частоты, задания удаления | По ключу; доставки и счётчики частоты — с TTL |
| *После MVP:* подписки и платёжные события, кэш AI-инсайтов | По ключу, по `user_id`, по id события; кэш — с TTL |

JOIN-ов, агрегаций, отчётов и поиска нет. Нужны три вещи:
- транзакция «записать пачку + увеличить счётчик версии пользователя»;
- диапазонное чтение по версии;
- автоматическая очистка по TTL.

### Сравнение классов БД именно под эти задачи

| Класс | Пример в РФ | Sync (диапазон по версии + атомарный счётчик) | Users / entitlements | Стоимость при 0 MAU | Путь до 50k | Миграция с текущего кода |
|---|---|---|---|---|---|---|
| **Managed PostgreSQL** | Yandex, Cloud.ru, Timeweb, Selectel | Отлично | Отлично | 790–3 350 ₽ (минимальный хост 24/7) | Вертикально, без переписывания | Минимальная (SQLAlchemy, Alembic) |
| PostgreSQL на VM / PaaS | Yandex VM, Timeweb VPS, Amvera | Отлично | Отлично | 780–1 720 ₽ | Ручной рост; при 10k+ лучше перейти на managed | Минимальная |
| Serverless PostgreSQL | **В РФ нет** ([обзор от 05.10.2026](https://habr.com/ru/companies/amvera/articles/1090478/)); Neon — только за рубежом | — | — | — | — | — |
| **YDB Serverless** | Yandex Cloud | Отлично: serializable-транзакции, PK `(user_id, …)`, глобальные индексы, TTL | Хорошо | **0 ₽** | Тот же API; есть выделенная пропускная способность и dedicated-режим | Слой данных переписывается (YQL), Alembic не нужен |
| Документная / key-value (YDB Document API, DynamoDB-совместимый) | Yandex Cloud | Хорошо, но транзакции и счётчик версий сложнее | Хорошо | 0 ₽ | Тот же | Слой данных переписывается |
| BaaS (Supabase, Firebase) | Российского аналога нет (см. §4) | Firestore / Realtime — да | Да | Firebase / Supabase free | — | Переписывание + оплата из РФ + 152-ФЗ |
| CloudKit (Apple) | — | Встроенный (`CKSyncEngine`) | Нет: entitlements всё равно нужны на своём backend | 0 ₽ | Бесплатно | iOS-код sync, backend не нужен для sync |

**Вывод.**
- PostgreSQL технически подходит идеально. Но его единственная проблема в РФ — нет serverless-режима, а это ровно приоритет №2 (0–100 MAU почти бесплатно).
- YDB Serverless закрывает те же задачи. Модель данных простая, ничего специфичного для PostgreSQL в ней больше нет.
- Сохранять PostgreSQL ради существующего кода не нужно. Код, который на нём держится (expenses, categories, calendar, analytics), всё равно удаляется в local-first.

> **Пересмотрено 13.10.2026 (D24).** Критерий «0 ₽ при нуле пользователей» уступил переносимости между провайдерами. Выбран PostgreSQL на ВМ (строка «PostgreSQL на VM / PaaS»): технически он подходит модели данных так же хорошо, а развёртывание и резервные копии не зависят от одного облака.

3. Контейнер 1 vCPU / 0,5 ГБ, плюс API Gateway.
   - 10k: CPU (21,8 ч − 5) × 5,69 = 95 + RAM 3 + API Gateway (605 тыс. − 100 тыс.) × 142,3 / 1 млн = 72.
   - 50k: CPU 551 + RAM 155 + вызовы 38 + API Gateway 416.
4. Автоматические бэкапы YDB за 2 дня бесплатны. Дополнительно — еженедельный экспорт в Object Storage с хранением 4 копий в холодном классе: 128 RU/МБ + 0,00176 ₽/ГБ·ч.
5. При 50k выгоднее включить [выделенную пропускную способность](https://yandex.cloud/ru/docs/ydb/pricing/serverless) 0,0184 ₽ за RU/с·ч. 40 RU/с × 720 ч × 0,0184 = 530 ₽ покрывают ~104 млн RU. Остаток ~11 млн RU по on-demand ≈ 280 ₽. Итого ~810 ₽ вместо 2 809. Это смена параметра, не кода.

**Фиксированно:** 24 ₽. **От запросов:** RU, контейнеры, API Gateway. **От объёма данных:** хранение YDB и экспорт.

## 7. Рекомендуемая архитектура (одна)

Решение D24 от 13.10.2026: переносимое развёртывание. Развёртывание и восстановление — [`deploy/portable`](../deploy/portable/README.md), аварийный план — [`disaster-recovery.md`](disaster-recovery.md).

### 7.1. Схемы

**Данные:**

```
iOS: UI ─ Local DB (SwiftData/GRDB, источник истины)
              │  outbox (несинхронизированные изменения)
              ↓↑  фоновой sync: на открытии приложения, после изменений (debounce), BGAppRefresh
        HTTPS (JWT) на домен API; DNS — вне провайдера сервера, TTL 300
              ↓↑
ВМ (Docker Compose, один сервер):
  Caddy: TLS Let's Encrypt, лимит тела запроса, HSTS     — профиль public, только production
  FastAPI (1 процесс uvicorn; лимиты частоты и параллельности — в процессе)
   ├─ /v1/auth/guest, /v1/auth/apple, /v1/auth/refresh, /v1/auth/logout
   ├─ /v1/sync/push, /v1/sync/pull                (только аккаунт; гостю — 403)
   ├─ /v1/imports/parse, /v1/imports/{id}/displayed (гость и аккаунт; 3 бесплатных учитываются без блокировки)
   ├─ /v1/me                                       (гость и аккаунт: features.imports; аккаунту — sync.lastVersion)
   ├─ DELETE /v1/account, GET /v1/account/deletions/{id}
   └─ /v1/apple/notifications                      (Sign in with Apple, server-to-server)
  maintenance: фоновые задачи (очистка tombstones, доставок, гостевых записей, доведение удалений) — команды
               внутри сети Compose, наружу не публикуются
  fence_check: проверка при старте, что домен API указывает на эту ВМ (дополнительная, не гарантия;
               единственный пишущий сервер обеспечивает подтверждённая остановка старого — disaster-recovery §5)
              ↓↑ сеть Compose, пароль из .env; порт БД не публикуется
PostgreSQL 16 (том pgdata):
   devices, users, identities, refresh_tokens, apple_tokens (шифротекст, ключ приложения),

   import_deliveries (срок 7 дн.), import_ledger, usage_counters, rate_counters,
   deletion_jobs, deleted_accounts (400 дн.)
   Сроки хранения — задачами maintenance (в PostgreSQL нет TTL)
backup: pg_dump каждые 6 ч → age (публичный ключ владельца) → S3 другого провайдера, 35 дней

AI Studio: только classify_transactions для нераспознанных операций импорта, по API-ключу; выключатель
Секреты: .env на сервере (600) + копия у владельца в менеджере паролей; ключ age — только у владельца

```

**Импорт выписки:**

```
iOS: файл (≤ 2 МБ) + активные категории (id, name) + подсказки categoryHints + Idempotency-Key
  → Caddy → FastAPI
      1. JWT (гость или аккаунт) → device_id / user_id; лимиты частоты, размера и параллельности (конфигурация)
      2. multipart в память (upload.py), файл нигде не пишется; корневая ФС контейнера read-only
      3. detect_format → registry → адаптер банка (детерминированный парсер, без AI)
      4. категоризация: правила → подсказки клиента → LLM только для оставшихся (≤ 500, маскированные

      5. ответ: importId, операции, предложенные категории; на сервере — только метаданные доставки
  → iOS: экран проверки → подтверждение показа (POST /v1/imports/{id}/displayed, надёжная очередь)

```

Учёт импортов, повтор по `Idempotency-Key` и клиентский контракт черновика — план §6.2, §6.5.

### 7.2. Почему именно она

1. **Переносимость.** Нужны только Linux-ВМ, Docker и S3 у любого провайдера. Перенос — `install.sh` + восстановление последней копии + смена A-записи домена; iOS-приложение не обновляется.
2. **Нет архитектурного тупика.** Модель sync и API свои; рост — вертикально (ВМ), затем Managed PostgreSQL того же провайдера без изменения кода, кроме строки подключения.
3. **Резервные копии вне провайдера.** Зашифрованы ключом владельца, сервер не может их расшифровать; учения восстановления — в CI (`drill.sh`).
4. **Local-first прощает простой.** При недоступности API аналитика, просмотр и ввод расходов работают офлайн, синхронизация ждёт (план §8.1). Поэтому для MVP достаточно восстановления за 1–2 ч без постоянно работающего резервного сервера.
5. **Переиспользуется код:** парсер выписок, маскирование ПДн, AI-клиент, JWT и ротация refresh-токенов, SQLAlchemy, Alembic, обработка ошибок.
6. **Работа и оплата из РФ.** Провайдер с площадкой в РФ (152-ФЗ); копии — у второго провайдера в РФ.

### 7.3. Стоимость MVP

Подробно — план §13. Фиксированная часть не зависит от числа пользователей до ~10k MAU: ВМ 1–2 vCPU / 2 ГБ с диском и IPv4 ≈ 2 200–3 000 ₽/мес, хранилище копий < 100 ₽/мес, домен — по тарифу регистратора. Переменная часть — AI-категоризация импорта.

### 7.4. Что первым станет узким местом

1. **CPU одного процесса uvicorn** при всплеске разборов выписок: на 2 vCPU × 50 % 8 одновременных импортов по 4 800 операций обработаны за 9,5 с (план §11.3). Ограничитель — `PARSE_CONCURRENCY_GLOBAL=4`.
2. **Один сервер — одна точка отказа.** Компенсируется копиями каждые 6 ч вне провайдера и аварийным планом (RTO ≈ 1–2 ч, RPO ≤ 6 ч, оценка).
3. **Лимиты в памяти процесса.** Корректны только при одном процессе; при нескольких процессах или серверах счётчики нужно перенести в PostgreSQL (`rate_counters`).
4. **AI** в MVP — только категоризация импорта; её ограничивают лимиты и выключатель.

### 7.5. Что сделать при 10k и 50k MAU

| Порог | Действие | Меняется код? |
|---|---|---|
| ~10k | ВМ 2–4 vCPU / 4 ГБ; `rate_counters` в PostgreSQL; 2 процесса uvicorn | Нет (лимиты уже в таблице к этому моменту) |
| ~50k | Managed PostgreSQL у провайдера ВМ (PITR), 2 ВМ приложения за балансировщиком | Только конфигурация |
| 100k+ | Реплики чтения для `sync/pull`, партиционирование `sync_records` по `user_id` | Слой репозиториев |

Переписывать API, sync или auth не придётся. Платежи после MVP добавляются по схеме §9.

## 8. Синхронизация (sync)

> **Статус: утверждено 09.10.2026** по итогам прототипа (`prototype/ydb-sync`, отчёт — `prototype/ydb-sync/REPORT.md`).
> Модель конфликтов — **вариант B**: `serverVersion + baseVersion`, outbox, инкрементальный pull по cursor, tombstones, идемпотентность по `mutationId`, delete wins. **HLC не используется.**

### 8.1. Модель

**Синхронизируются только пользовательские данные, которым нужно облачное хранение:**

| Сущность | Что это | Удаление |
|---|---|---|
| `Expense` | **Одна сущность** для ручных и импортированных расходов. Импортированная операция после проверки пользователем сохраняется обычным расходом, название операции из выписки — в `comment`. Отдельного признака источника нет: после сохранения расходы одинаково отображаются, редактируются, удаляются, участвуют в аналитике и синхронизируются | Tombstone (`deletedAt`), delete wins |
| `Category` | Системные (константы приложения со стабильными UUID) и пользовательские. Поле `isArchived`. **Системные архивируются наравне с пользовательскими, кроме резервной «Другое»:** их состояние синхронизируется записью с тем же UUID и payload `{kind: "system", isArchived}` — без дублирования категории (план миграции §3.2) | **Не удаляется, а архивируется**: архивная категория недоступна для новых расходов, существующие расходы сохраняют связь с ней, историческая аналитика её показывает. Разархивирование — после MVP |
| `DayMark` («День без расходов») | `entityId = UUIDv5(дата)`, payload `{date, isMarked}`; снятие — `isMarked=false`, не удаление. Расход всегда главнее отметки; увидев расход на отмеченную дату, клиент снимает отметку; после удаления последнего расхода отметка не восстанавливается (план миграции §4) | Не удаляется (`op=delete` запрещён) |

**Не синхронизируются и остаются только на устройстве:** `app_settings`, локальный черновик импорта, технические состояния UI. У sync API нет для них типа сущности (push → `422`).

**Повторный импорт не проверяется на дубликаты.** Пользователь сам отвечает за повторную загрузку одной выписки; автоматического обнаружения дубликатов нет.

**Payload:**

```
Expense   { amount: "250.50", categoryId: uuid, date: "2026-10-01", comment?: string ≤ 200 }
          comment: NFC, ≤ 200 кодовых точек; импорт обрезает по границе графем (план миграции §3.3)
Category  { kind: "user", name: 1–24, emoji: 1 графема, colorIndex, sortOrder?, isArchived }
        | { kind: "system", isArchived }            ← только для id из реестра системных категорий
DayMark   { date: "2026-10-01", isMarked: bool }
```

**Общие поля каждой записи:**

| Поле | Кто задаёт | Назначение |
|---|---|---|
| `id` (UUID) | Клиент при создании | Стабильный глобальный id; повтор не создаёт дубль. Системные категории — фиксированные UUID |
| `entity_type` | Клиент | `expense` / `category` |
| `created_at`, `updated_at` | Клиент (часы устройства) | `updatedAt` используется **только** для выбора победителя между конкурентными правками; сервер обрезает значения дальше `now + 5 мин` |
| `deleted_at` | Клиент | Tombstone: удаление = запись с `deletedAt` и пустым payload |
| `device_id` | Клиент | Диагностика и детерминированный разрыв ничьей. **Приоритета не даёт** |
| `schema_version` | Клиент | Версия формата payload |
| `version` | **Сервер** | Монотонный номер изменения внутри пользователя: и cursor для pull, и основа для `baseVersion` |
| `order_ts` | Сервер | Монотонная метка записи `max(updatedAt, order_ts основы)` для конкурентных конфликтов |
| `mutation_id` | Сервер (из мутации) | Какая мутация дала текущее состояние: повтор после истечения журнала → `noop` |
| `payload` (JSON) | Клиент | Поля сущности. Сервер проверяет тип, размер и обязательные поля, но не связи между сущностями |

**Таблицы YDB:**

```
sync_records    PK (user_id, entity_type, entity_id)
                version, created_at, updated_at, deleted_at, order_ts, device_id, schema_version,
                mutation_id, payload Json
                INDEX by_version GLOBAL SYNC ON (user_id, version) COVER (...)
sync_state      PK (user_id)    last_version, tombstone_horizon
sync_mutations  PK (user_id, mutation_id)    request_hash, result Json, created_at   TTL 30 дней
```

Индекс `by_version` — обязательно **GLOBAL SYNC**: асинхронный индекс eventual и ломает pull по курсору.

### 8.2. Протокол

**`POST /v1/sync/push`**

```json
{ "deviceId": "...", "mutations": [
  { "mutationId": "uuid", "entityType": "expense", "entityId": "uuid", "op": "upsert",
    "baseVersion": 41, "createdAt": "...", "updatedAt": "...", "deletedAt": null,
    "schemaVersion": 1, "payload": {...} } ] }
```

- До 500 мутаций или 1 МБ за запрос. Клиент отправляет outbox пачками в порядке создания.
- Пачка обрабатывается **одной serializable-транзакцией YDB** (2 обращения к YDB: чтение и запись + commit). Конкурентные push одного пользователя сериализуются через строку `sync_state` (OCC).
- Правила для каждой мутации:
  1. `mutationId` уже в журнале → вернуть сохранённый результат (**идемпотентность**); тот же id с другим телом → `mutation_id_reused`;
  2. записи нет: `baseVersion == 0` → создать; `baseVersion > 0` → запись была удалена и её tombstone очищен → `rejected/deleted` (удаление — `noop`). Удалённый расход не воскресает;
  3. запись удалена → любое изменение `rejected/deleted`, повторное удаление `noop` (**delete wins**);
  4. удаление применяется всегда;
  5. `baseVersion == version` → правка основана на актуальном состоянии: применить. Часы не участвуют;
  6. иначе — конкурентная правка (конфликт):
     - категории: **archive wins** — архивирование побеждает, правка архивной категории без архивирования отклоняется;
     - остальное: LWW по записи — побеждает больший `(updatedAt, deviceId)` относительно `order_ts` текущей записи.
- **`deviceId` не даёт приоритета.** Совпадение устройства с автором последней правки не делает устаревшую правку актуальной. Последовательные офлайн-правки одного устройства получают актуальную базу перебазированием:
  - внутри одной пачки — на сервере (правка с той же базой, что предыдущая правка записи в пачке, перебазируется на выданную ей версию; в том числе при повторе пачки из журнала);
  - между пачками — на клиенте: после `applied` более поздние мутации этой записи в outbox получают новую `baseVersion`.
- Ответ на каждую мутацию: `applied` + `version`, `rejected` (`conflict` | `deleted`) или `noop`; поле `record` с актуальной серверной записью, если клиенту нужно её применить. Нет `record` у неприменённой мутации → записи на сервере нет, клиент удаляет её локально.
- Исчерпаны повторы транзакции или троттлинг RU → `503` + `Retry-After`; клиент повторяет (push идемпотентен).

**`GET /v1/sync/pull?cursor=<version>&limit=500&horizon=<h>`**

- `SELECT … WHERE user_id = $u AND version > $cursor ORDER BY version LIMIT 500` по индексу `by_version` (snapshot-чтение).
- Ответ: `{ records, nextCursor, hasMore, horizon }`. Клиент сохраняет страницу, курсор и `horizon` одной локальной транзакцией и присылает `horizon` в следующем запросе.
- `410 resync_required` — только если клиент мог пропустить очищенные удаления: `cursor > 0`, `cursor < tombstone_horizon` **и** присланный `horizon < tombstone_horizon` (горизонт сдвинулся после прошлого ответа). Без третьего условия постраничная загрузка с нуля после очистки получала 410 на второй странице и зацикливалась.

**Применение на клиенте:**
- Входящая запись заменяет локальную, если по ней нет неотправленных мутаций и её `version` не меньше локальной.
- Есть неотправленная мутация → локальное состояние остаётся; конфликт решит сервер, ответ push вернёт авторитетную запись.

### 8.3. Почему так

- **`baseVersion` вместо HLC.** Причинность («правка сделана после того, как устройство увидело версию N») доказывает номер версии, выданный сервером, а не часы устройства. Неверные часы влияют только на выбор между действительно конкурентными правками. Клиенту не нужно вести и сохранять HLC; в протоколе нет поля, которое можно «отравить» часами из будущего.
- **LWW по записи**, а не по полю и не CRDT: финансовый трекер, 1–2 устройства, редкие одновременные правки одной записи. Просто, предсказуемо, легко тестируется. Переход на LWW по полю возможен без смены протокола.
- **Delete wins / archive wins.** Удаление и архивирование — явные намерения пользователя; конкурентная правка не должна их отменять. Обратная операция (разархивирование) — отдельное действие после MVP.
- Проверено прототипом: 4 000 рандомизированных историй (2–4 устройства, часы со сдвигом до суток, офлайн, потерянные ответы, обрывы pull, очистка tombstones и вынужденные resync, архивирование) — ни одного расхождения, потерянного обновления, воскрешения удалённой записи или отмены архивирования.

### 8.4. Сценарии

| Сценарий | Поведение |
|---|---|
| **Изменения офлайн** | Пишутся в Local DB и outbox одной локальной транзакцией; UI не ждёт сети; push при появлении сети с экспоненциальной задержкой |
| **Последовательные офлайн-правки одной записи** | Применяются по порядку без конфликтов благодаря перебазированию (в пачке — сервер, между пачками — клиент) |
| **Повтор запроса / обрыв связи** | Тот же `mutationId` → тот же результат; pull идемпотентен. Мутация удаляется из outbox только после ответа сервера |
| **Сбой посреди пачки** | Транзакция атомарна: пачка применена целиком или не применена. Клиент повторяет |
| **Два устройства** | Каждое делает push и pull, курсор у каждого свой. Правка на актуальной версии применяется; конкурентные — по правилам §8.2 |
| **Удаление против редактирования** | Delete wins в любом порядке синхронизации |
| **Архивирование категории** | Обычная правка `isArchived = true` (для системной — запись состояния с её UUID), синхронизируется как поле. Archive wins против конкурентной правки. Клиент не даёт выбрать архивную категорию для нового расхода или перенести в неё расход. Ссылка на ещё не полученную категорию допустима: плейсхолдер до завершения загрузки |
| **Вход через Apple ID** | Данные есть и локально, и в облаке → диалог «Объединить данные» (по умолчанию) / «Заменить локальные данные облачными» (с предупреждением). До выбора локальные данные не отправляются. Одна сторона пустая → без диалога (план миграции §2.3) |
| **Новый iPhone** | Вход → полная загрузка с cursor 0 страницами (тот же возобновляемый путь, что resync) → дальше обычный режим |
| **Объединение / первичная загрузка local → cloud** | Полная загрузка облака, затем локальные записи уходят созданиями пачками (категории раньше расходов); общие id (состояния системных категорий, отметки дня) — по обычным правилам конфликтов |
| **Очистка tombstones** | Задача по таймеру удаляет tombstones старше 180 дней и сдвигает `tombstone_horizon` (горизонт не убывает) одной транзакцией |
| **Долгое отсутствие → `410 resync_required`** | Клиент: 1) не удаляет локальные изменения и сохраняет outbox; 2) загружает состояние сервера с cursor 0 страницами, сохраняя прогресс (`resync_cursor`) и полученные ключи — после обрыва или перезапуска продолжает с места остановки, а если горизонт снова сдвинулся — начинает заново; 3) записи с неотправленными правками не перезаписывает; 4) в конце одной транзакцией удаляет локальные записи, которых нет ни на сервере, ни в outbox (их tombstones очищены); 5) отправляет outbox: правки согласуются по обычным правилам, новые расходы создаются, правки давно удалённых записей сервер отклоняет как `deleted` — они не восстанавливаются |
| **Изменение схемы payload** | `schemaVersion` в записи. Сервер принимает известные версии; клиент мигрирует данные при чтении. Старый клиент получает `426 upgrade_required` на неизвестную версию |
| **Ручной выход (кнопка «Выйти»)** | Одно предупреждение → сразу, без синхронизации, удаляются локальные расходы, категории, отметки дня, outbox, sync state, черновик импорта и настройки аккаунта; несинхронизированные изменения теряются; облако и общие настройки устройства сохраняются; приложение — в гостевом режиме (план миграции §2.4) |
| **Отзыв доступа Apple (`consent-revoked`)** | Сессии и синхронизация прекращаются (`401 session_revoked`); локальные данные, outbox и sync state **не удаляются**; клиент показывает необходимость повторного входа. Вход тем же Apple ID — продолжение sync без диалога объединения: outbox доставляется с прежними `mutationId`; другим Apple ID — только через ручной выход (план миграции §2.6, §2.9) |
| **Удаление аккаунта** | `DELETE /v1/account`: возобновляемое задание — отзыв токена Sign in with Apple, пачечное удаление всех строк пользователя, отзыв сессий. Устройство удаляет локальные данные и настройки аккаунта (`app_settings` устройства сохраняются); остальные устройства очищаются по `401 account_deleted` (план миграции §2.5) |
| **Неактивность** | Apple-аккаунты в MVP автоматически не удаляются. Гостевые технические записи устройства очищаются через 12 месяцев с последнего запроса устройства; устройство, вошедшее в аккаунт, считается активным по claim `did` (план миграции §2.7) |

### 8.4a. Проверено в Yandex Cloud (09.10.2026)

> Замеры прототипа на YDB. Правила sync (§8.1–§8.4) подтверждены и переносятся на PostgreSQL без изменений; метрики RU, холодного старта и лимита 10 RU/с к выбранной архитектуре (D24) не относятся.

Прототип развёрнут в Serverless Containers + API Gateway + YDB Serverless (лимит 10 RU/с), все e2e-проверки прошли, ресурсы удалены. Подробно — `prototype/ydb-sync/REPORT.md` §P2.3.

| Метрика | Значение |
|---|---|
| Холодный старт (простой ≥ 5 мин) | 3,8–4,0 с; тёплый `/health` 0,15 с, push 8 — 0,33 с, pull 10 — 0,20 с (p50) |
| RU push | ≈ 6 на мутацию + 3–5 на запрос (правка — 9–16 RU) |
| RU pull | ≈ 2 на запись + 2 на запрос |
| RU первых запросов новой сессии | +250…950 (компиляция) — основная статья при редком трафике; пул сессий 1–2 |
| Лимит 10 RU/с | достаточен для MVP: 3 выгрузки по 1 000 записей подряд без `503`, троттлинг — задержкой до 26 с на push. Для первичной выгрузки пачки ~100 мутаций |
| MVP, 20 пользователей | ≈ 0,8 млн RU/мес — в бесплатном объёме |

**Известное ограничение.** Если ответ на создание записи потерян, устройство не выходит в сеть дольше срока хранения tombstones (180 дней), а за это время запись удалили на другом устройстве и tombstone очищен, повтор создания восстановит её. Сервер не может отличить «создание не доходило» от «создано и давно удалено». Для MVP вероятность пренебрежимо мала.

### 8.5. Аутентификация

- **`POST /v1/auth/apple`** `{identityToken, authorizationCode, nonce}`:
  - проверка JWT по ключам Apple (`aud` = bundle id, `nonce`);
  - обмен `authorizationCode` на refresh-токен Apple. Он нужен, чтобы отозвать доступ при удалении аккаунта; хранится зашифрованно;
  - поиск или создание пользователя по `(apple, sub)`;
  - выдача своих access JWT (15 мин) и refresh (ротация, grace-окно и обнаружение повторного использования — **существующая логика**).
- **Гостевая техническая запись устройства** (`POST /v1/auth/guest`) нужна для технических запросов: импорт и учёт бесплатных импортов. Финансовых данных гостя на сервере нет, `/sync/*` для гостя закрыт. Гость не повышается до аккаунта: после выхода устройство продолжает использовать свою запись (план §2.2).
- Server-to-server уведомления Sign in with Apple (официальные типы: `email-disabled`, `email-enabled`, `consent-revoked`, `account-deleted`) обрабатываются идемпотентно: `consent-revoked` завершает сессии и sync без удаления локальных данных и outbox (`401 session_revoked`, повторный вход восстанавливает sync), `account-deleted` запускает удаление аккаунта (план миграции §2.6).
- Коды 401 различаются: `token_expired`, `refresh_token_invalid`, `session_revoked`, `account_deleted`; статус удаления доступен по гостевому токену того же устройства (план миграции §2.5, §2.8).
- Таблица `identities(provider, subject → user_id)` позволит добавить Android-вход (Google, VK ID) без изменения модели.
- Email из Apple не храним (минимизация ПДн), если он не нужен для продукта.

## 9. Premium и платежи — после MVP (архитектурный задел)

> **В MVP ничего из этого раздела не реализуется:** нет покупок, подписок, StoreKit-платежей, эквайринга, paywall и ограничений платного доступа. Облачная синхронизация и вся аналитика бесплатны всегда, независимо от Premium.
>
> **В MVP есть только** учёт 3 бесплатных подтверждённых импортов (`import_ledger`, `usage_counters`, `import_deliveries`) и флаг `ENFORCE_QUOTAS=false`: исчерпание лимита импорт не блокирует. `GET /v1/me` отдаёт `features.imports`, а функция `feature_state` готова к будущим правам доступа (план §5, §6).
>
> Ниже — схема, по которой Premium будет добавлен после MVP. При реализации её уточнят отдельным решением.

**Таблицы:**

```
entitlements    PK (user_id, source)      source: app_store | external
                status: active | grace | billing_retry | expired | revoked | refunded
                product_id, expires_at, auto_renew, original_transaction_id / provider_subscription_id,
                environment (sandbox | production), updated_at
payment_events  PK (provider, event_id)   received_at, processed_at, status, payload_hash
billing_subscriptions  (только для внешнего эквайринга)
                PK (user_id)  payment_method_id, plan, next_charge_at, cancel_at_period_end
```

Учёт квот берётся из таблиц MVP (`usage_counters`, `import_ledger`); с включением оплаты `ENFORCE_QUOTAS=true`.

**Правило:** `premium = any(e.status ∈ {active, grace} and e.expires_at + grace > now)`. Источник покупки не важен. Клиент получает entitlement в `/v1/me`, кэширует `expiresAt` и не определяет Premium только по локальному StoreKit. Premium-функции и так требуют backend, поэтому проверка на сервере авторитетна.

**App Store** ([App Store Server Notifications V2](https://developer.apple.com/documentation/appstoreservernotifications)):
- покупка с `appAccountToken = user_id`;
- клиент присылает подписанные транзакции (JWS) → сервер проверяет цепочку подписи Apple;
- webhook обрабатывает `SUBSCRIBED`, `DID_RENEW`, `DID_FAIL_TO_RENEW` (→ grace / billing_retry), `GRACE_PERIOD_EXPIRED`, `EXPIRED`, `REFUND`, `REVOKE`;
- restore = `AppStore.sync()` на клиенте + повторная отправка транзакций; сервер может сверить статус через App Store Server API.

**Российский эквайринг** (например, [ЮKassa](https://yookassa.ru/developers/using-api/webhooks)):
- оплата на сайте, сохранённый способ оплаты для автоплатежей;
- webhook `payment.succeeded`, `payment.canceled`, `refund.succeeded`;
- проверка: IP-allowlist + запрос актуального статуса объекта по API; ЮKassa повторяет уведомления 24 ч;
- продление — ежедневный таймер-триггер; отмена — `cancel_at_period_end`;
- фискализация чеков по 54-ФЗ — средствами провайдера.

**Идемпотентность:** `payment_events` с PK `(provider, event_id)`. Повтор → `200` без повторной обработки. Обработка — переход статуса в транзакции вместе с записью события.

**Важные ограничения, не юридическое заключение:**
- С 1 апреля 2026 у российских пользователей фактически нет массового способа оплаты App Store, кроме подарочных карт ([РБК](https://companies.rbc.ru/news/bJgt0NJESj/kak-popolnit-app-store-i-oplatit-podpiski-apple-id-v-rossii-v-2026-godu/)). Поэтому внешний эквайринг будет основным источником дохода в РФ.
- [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/):
  - 3.1.1 — разблокировка функций в приложении должна идти через In-App Purchase;
  - 3.1.3(b) — подписку, купленную на других платформах или сайте, можно использовать в приложении, если она также доступна через IAP;
  - вне витрины США в приложении **нельзя давать кнопки и ссылки на внешнюю оплату**.
- Значит: IAP в приложении + оплата на сайте без ссылок из приложения + общий entitlement на backend. Именно это даёт предложенная модель.
- При удалении аккаунта: подписку российского эквайринга сервер отменяет автоматически; для подписки App Store клиент предупреждает и даёт перейти к управлению подпиской (план §2.5).

## 10. AI-слой и аналитика

### 10.0. Аналитика MVP — алгоритмическая, на устройстве

Девять видов, бесплатно, без LLM, детерминированно. Считаются на iOS из локальной БД, полностью офлайн, без сообщений об интернете, у гостя и у аккаунта:

1. сравнение периодов;
2. категории — доли и сравнение;
3. средние за день и за период;
4. самые дорогие даты;
5. дни недели — нормализация по числу учтённых дней этого дня недели и разложение вклада категорий;
6. тренды категорий — оценка Тейла — Сена;
7. повторяющиеся платежи и регулярные траты;
8. необычные расходы и отклонения — медиана и MAD;
9. прогноз до конца месяца.

Общая основа — **учтённые дни**: дни с расходами плюс отметки «без расходов» (0 ₽); неучтённый день — неизвестность, а не ноль. Константа среднего месяца — 30,4375 дня, суммы в целых копейках.

Формулы, минимумы истории, неполные периоды и пограничные случаи — план §7. **Реализация на iOS обязана проходить Python-эталон и тест-векторы этапа A1** (проверка в CI iOS). Сервер аналитику не считает и не хранит.

## 11. Безопасность и 152-ФЗ

| Аспект | Решение |
|---|---|
| TLS | Caddy + Let's Encrypt на домене API, HSTS. Без домена (тестовый стенд) Caddy не запускается, API доступен только через SSH-туннель |
| Сеть | Снаружи только 22, 80, 443 (тестовый стенд — только 22). API слушает `127.0.0.1`, порт PostgreSQL не публикуется; проверка — `deploy/portable/check_exposure.py` в CI и на сервере. SSH — только по ключу |
| Доступ к БД | Только из сети Compose по паролю из `.env`; один пользователь приложения; миграции Alembic — отдельный сервис `migrate` |
| Секреты | `.env` на сервере (права 600): `POSTGRES_PASSWORD`, `JWT_SECRET`, `TOKEN_DERIVATION_SECRET`, ключ шифрования Apple-токенов, ключ Apple `.p8` и `kid`, Team ID, API-ключ AI Studio. Копия — у владельца в менеджере паролей. В git, metadata ВМ и чатах значения не появляются |
| Шифрование | TLS в транзите. Apple refresh-токены — шифрование ключом приложения (AES-GCM, `aad = user_id`, ключ в `.env` и у владельца), используются только для отзыва при удалении аккаунта (план D13). Шифрование payload на стороне клиента (E2E) не делаем |
| Бэкапы | Каждые 6 ч `pg_dump` → age на публичный ключ владельца → S3 другого провайдера; хранение 35 дней (отразить в политике конфиденциальности: удалённые данные остаются в копиях до 35 дней). Восстановление проверяется `drill.sh` в CI и перед production на реальной инфраструктуре |
| Выписки | Только в памяти, не сохраняются; лимит 2 МБ (D12); корневая ФС контейнера read-only |
| Логи | Белый список полей: маршрут, статус, длительность, `requestId`, HMAC субъекта, счётчики. Без тел, сумм, комментариев, названий категорий, содержимого и имён файлов выписок, токенов, кодов Apple и query string (план §10) |
| ПДн в синхронизируемых данных | Комментарии импортированных операций могут содержать ФИО получателей переводов. В MVP название операции записывается в `comment` как есть (план §3.3). Маскирование перед sync — кандидат на продуктовое решение после MVP |
| 152-ФЗ | Сервер и копии — у провайдеров с площадками в РФ. Уведомление РКН как оператора ПДн, политика конфиденциальности, согласие при создании аккаунта, удаление по запросу (план §2.5). AI — только категоризация в AI Studio (РФ), маскированные описания, `x-data-logging-enabled: false`. Не юридическое заключение |

## 13. Финальная рекомендация

**Money Planner MVP: одна ВМ у провайдера с площадкой в РФ — Docker Compose (Caddy, FastAPI, PostgreSQL 16), внешний домен, зашифрованные копии каждые 6 ч у второго провайдера; AI Studio — только категоризация импорта по API-ключу.** Решение D24 от 13.10.2026.

**Почему:**
- переносится к другому провайдеру за ≈ 1–2 ч без изменения кода и без обновления iOS-приложения;
- PostgreSQL штатно закрывает модель данных sync; используется существующий стек (SQLAlchemy, Alembic);
- проверено на тестовом стенде 2 vCPU × 50 % / 2 ГБ (синтетические данные, план §11.3).

**Где проиграет:**
- фиксированные ≈ 2 200–3 000 ₽/мес даже без пользователей;
- одна ВМ — одна точка отказа; восстановление по плану, а не автоматически;
- администрирование ОС, обновлений и копий — на команде.

**Сейчас:** существующая ВМ Yandex Cloud — тестовый стенд (не production). **Следующий шаг:** этап E1 на PostgreSQL (план §11).
