### 3.3. Данные backend по local-first архитектуре и цена их потери [О]

По плану rev. 5.1 источник истины — устройство, сервер хранит копию для синхронизации и служебные данные.

| Данные сервера (план §7.1) | Последствия потери |
|---|---|
| `devices`, `refresh_tokens` | все выходят из сессий: гость пересоздаётся автоматически, аккаунтам нужен повторный вход через Apple |
| `users`, `identities` | вход через Apple создаст новый аккаунт с другим `user_id` |
| `sync_records`, `sync_state`, `sync_mutations` | **облачная копия расходов теряется**. Устройства сохраняют локальные данные, но новое устройство восстановить нечего. Если клиент не умеет распознать «сервер потерял данные», состояние разойдётся (см. рекомендацию 6.3) |
| `import_ledger`, `usage_counters` | счётчики бесплатных импортов обнуляются; в MVP квоты не блокируют — влияние низкое |
| `apple_tokens` (шифротекст KMS) | невозможно отозвать токены Apple при удалении аккаунта. **Потеря ключа KMS делает невосстановимыми и копии этой таблицы** |
| `deletion_jobs`, `deleted_accounts` | начатые удаления аккаунтов не будут завершены — юридический риск |

В **текущем коде** (PostgreSQL) сервер — источник истины для расходов, категорий и календаря: потеря БД означает полную потерю данных пользователей.

### 3.5. Хватит ли переноса одной ВМ

**Нет** [О]. Схема `deploy/README.md` требует Lockbox, Managed PG, Container Registry, Cloud Logging и metadata-IAM. Перенесённая ВМ не получит секреты (нет metadata-сервиса), не скачает образ, не подключится к БД. Поэтому подготовлено отдельное переносимое развёртывание (раздел 4).

## 6. Рекомендации

1. **Оставаться ли на текущем окружении.** Оставаться не на чем: production не запущен. Срочно переносить нечего — данных нет. Остановленную ВМ можно не трогать: она ничего не обслуживает. Решение об удалении — после осмотра диска.
2. **Где запускать production.** Пока Yandex Cloud в аварийном режиме и не выдаёт квоты, новый production в нём не запускать. Для текущего кода использовать `deploy/portable` у другого провайдера (раздел 5).
3. **Резервный сервер.** Постоянно работающий резервный сервер для MVP не нужен [О]. Приложение local-first: при недоступности API аналитика и учёт работают офлайн, а синхронизация ждёт. Достаточно внешних зашифрованных копий каждые 6 ч, готового аккаунта у второго провайдера, домена вне провайдера и регулярных учений. Цель — RTO 1–2 ч, RPO ≤ 6 ч. Резервный сервер имеет смысл, когда простой в 1–2 ч станет неприемлемым для бизнеса.
4. **Целевая архитектура (план rev. 5.1) — пересмотреть до E1** [О]. Полностью serverless-стек Yandex не переносится к другому провайдеру без переписывания. Варианты:
   - (a) оставить PostgreSQL и Docker-развёртывание: sync-протокол по плану, хранилище — PostgreSQL, бэкапы как в `deploy/portable`. ≈ 2 500–3 000 ₽/мес вместо 25–60 ₽, зато переносимо за час;
   - (b) оставить YDB, но добавить регулярный экспорт во внешний S3 и шифрование Apple-токенов ключом, который хранится вне KMS.
   
   Решение за владельцем продукта.
5. **Домен API — сразу и вне Yandex.** iOS-клиент должен ходить только на него (не на `*.apigw.yandexcloud.net`). Это единственный способ переключить сервер без релиза приложения.
6. **Контракт sync: признак «сервер потерял данные».** Добавить в `/me` и `/sync/pull` идентификатор поколения хранилища (`serverEpoch`): при смене клиент заново отправляет полное локальное состояние. Тогда потеря облачной копии восстановится с устройств. Это изменение контракта E0 — отдельная задача.
7. **Гигиена:** удалить устаревшую запись 81.26.191.165 из `~/.ssh/known_hosts` (`ssh-keygen -R 81.26.191.165`) — адрес может достаться другому клиенту облака.
