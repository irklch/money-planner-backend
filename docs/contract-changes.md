# Изменения API-контракта относительно Figma (08 — Endpoint Contracts, 09 — Error Model)

Машиночитаемый контракт — `openapi.json`. Изменения внесены в Figma «Money Planner — API Architecture» 2026-10-04: страница 08 (карточки и вводный текст), 09 (`invalid_request`, `idempotency_key_reused`, правила для iOS), 11 (`expense_imports`, связи и правила).

## 1. Заголовок `X-Timezone` («сегодня» в часовом поясе пользователя)

iOS передаёт IANA-идентификатор часового пояса устройства, например `X-Timezone: Europe/Moscow`. Сервер вычисляет «сегодня» в этом поясе и проверяет по нему `date ≤ сегодня`. Даты расходов остаются календарными датами `YYYY-MM-DD` и в UTC не преобразуются.

| Endpoint | X-Timezone |
|---|---|
| `POST /expenses` | обязателен |
| `PATCH /expenses/{id}` | обязателен, если в теле есть `date`; рекомендуется отправлять всегда |
| `POST /expenses/import` | обязателен |
| `PUT /calendar/acknowledgements/{date}` | обязателен |

Новые ошибки — `400 invalid_request` с `details`:

- `{ "field": "X-Timezone", "code": "timezone_required" }`: заголовок отсутствует или пуст;
- `{ "field": "X-Timezone", "code": "timezone_invalid" }`: передано не IANA-имя (например, `+03:00`).

## 2. `POST /auth/anonymous`: повтор с тем же Idempotency-Key

- В течение 24 ч, пока выданный refresh-токен **не использован, не отозван и не истёк**, ответ `201` с `Idempotent-Replayed: true` возвращает того же guest и тот же `refreshToken` / `refreshTokenExpiresAt`. `accessToken` выдаётся новый: это JWT того же `userId`, он не хранится, поэтому повторить прежний невозможно и не нужно.
- В остальных случаях (токен уже ротирован через `/auth/refresh`, отозван, истёк или 24 ч прошли) возвращается **`409 idempotency_key_reused`** без токенов. Нового guest не создаётся. Это defensive-ошибка: в штатном flow клиент, который уже воспользовался токеном, ключ не повторяет. Код нужно добавить в список ERRORS карточки.

## 3. `POST /expenses/import`: отпечаток тела и сохранённый результат (миграция 0003)

В `expense_imports` добавлены поля `request_hash` (SHA-256 нормализованного тела), `imported_count`, `date_from`, `date_to`. Они записываются в одной транзакции с расходами.

Как работает повтор:
- **Тот же ключ и то же тело** → `201` с сохранённым результатом первоначального сохранения и заголовком `Idempotent-Replayed: true`. Если расходы потом меняли или удаляли, ответ повтора от этого не меняется.
- **Тот же ключ и другое тело** (или ключ другого пользователя) → `409 idempotency_key_reused`.
- **Первый запрос ещё выполняется** → `409 idempotency_in_progress` с заголовком `Retry-After`.

Как нормализуется тело перед хешированием. Хеш считается по провалидированной модели, поэтому порядок ключей JSON и форматирование на него не влияют.
- `amount` приводится к строке с 2 знаками;
- `date` записывается как `YYYY-MM-DD`;
- `categoryId` — UUID в каноническом виде;
- `comment` обрезается по краям, пустой или отсутствующий превращается в `null`;
- порядок операций — часть тела.
