## 0. Коротко

**Состав MVP [У]:**
- гостевой режим (данные только на устройстве);
- Sign in with Apple с бесплатной облачной синхронизацией `Expense`, `Category`, `DayMark`;

- **девять видов алгоритмической аналитики — локально, бесплатно, без AI и без интернета** (§7).

**Вне MVP [У]:**
- AI-инсайты (§14);
- Premium и оплата;
- автоматическое удаление неактивных Apple-аккаунтов (§2.7).

**Стек [У]:** API Gateway → Serverless Container (FastAPI) → YDB Serverless; AI Studio — только для категоризации операций, которые не распознали правила и подсказки. Секреты в Lockbox, ключ шифрования в KMS.

**Протокол sync [У]:** без изменений: `baseVersion`, outbox, cursor/`horizon`, tombstones, resync после `410`, delete wins, archive wins.

**Сроки:** около **35–46 рабочих дней** одного разработчика backend:

- A1 (эталон аналитики) — ≈ 3–4 дня, параллельно.

## 2. Пользователи, режимы и жизненный цикл данных

### 2.1. Что где хранится

| Данные | Гость | Аккаунт Apple | После выхода из Apple ID | После удаления аккаунта |
|---|---|---|---|---|
| Expense, пользовательские Category, состояние системных категорий, отметки дня | только локально | локально + облако | удаляются локально, облако сохраняется | удаляются везде |
| Outbox, cursor, horizon, resync-state, ожидание выбора при входе | — | локально | удаляются | удаляются |
| Черновик импорта | локально (на сервере не хранится никогда) | локально | удаляется | удаляется |
| Общие настройки устройства | локально | локально, не синхронизируются | сохраняются | сохраняются |
| Настройки, связанные с аккаунтом | — | локально | очищаются | очищаются |
| Системные категории (константы, стабильные UUID) | в приложении | в приложении | остаются; состояние архивирования сбрасывается | то же |
| Гостевая техническая запись устройства | `devices` + refresh-токены | остаётся привязанной | используется снова | используется снова |
| Учёт импортов | счётчик устройства | счётчик аккаунта + счётчик устройства (§6.1) | показывается счётчик устройства (не сбрасывается) | счётчик аккаунта удаляется; счётчик устройства остаётся |
| Apple refresh token | — | шифротекст KMS | остаётся | отзывается и удаляется |

**Настройки, связанные с аккаунтом [У + Т]:**
- кэш профиля и статуса аккаунта;
- статус и время последней синхронизации;
- кэш счётчика импортов аккаунта;
- флаги выбора при входе и онбординга аккаунта.

Общие настройки устройства (тема, валюта отображения, напоминания, параметры аналитики по умолчанию) сохраняются.

### 2.2. Гостевая техническая запись [Т]

- `POST /v1/auth/guest` (бывший `/auth/anonymous`; идемпотентный повтор и ротация refresh переносятся как есть) создаёт `devices(device_id, created_at, last_seen_at)`. Refresh-токен хранится в Keychain (`AfterFirstUnlockThisDeviceOnly`).
- Все токены (гостевые и аккаунта) содержат claim `did` — id устройства. `devices.last_seen_at` обновляется не чаще раза в сутки при **любом** запросе устройства, включая запросы под аккаунтом. Поэтому запись устройства, вошедшего в аккаунт, не считается неактивной.
- Гость не «повышается» до аккаунта: аккаунт — отдельная сущность `users(kind=account)`.
- Гостю доступны: `/imports/*` [У], `/me`, `/auth/refresh`. `/sync/*` → `403 account_required`.

### 2.3. Вход через Apple ID [У]

**Сервер:**
- `POST /v1/auth/apple { identityToken, authorizationCode, nonce }` с гостевым токеном;
- проверка JWT по JWKS Apple: `iss`, `aud` = bundle id, `exp`, хэш `nonce`;
- немедленный обмен `authorizationCode` на Apple refresh token (код действует ~5 мин), шифрование в KMS (`aad = user_id`);
- найти или создать `users(kind=account)` по `identities(apple, sub)`, связать устройство;
- атрибуция гостевых импортов устройства (§6.1);
- ответ: `sync: { lastVersion, hasData }`.

**Клиент — до любой отправки данных:**

| Локально есть данные* | В облаке есть данные | Действие |
|---|---|---|
| нет | нет / есть | полная загрузка с cursor 0, без диалога |
| есть | нет | загрузка локальных данных в облако, без диалога |
| есть | есть | диалог: **«Объединить данные»** (по умолчанию) / **«Заменить локальные данные облачными»** (с предупреждением) |

\* Расходы, пользовательские категории, архивированные системные категории, отметки дня.

- До выбора локальные данные не отправляются. В гостевом режиме outbox не ведётся. Состояние «ожидает выбора» хранится локально, sync до выбора выключен.
- **Объединить:** полная загрузка облака → локальные записи уходят созданиями (`baseVersion 0`), категории раньше расходов → обычные правила конфликтов. Для общих id (системные категории, отметки дня) — archive wins и LWW.
- **Заменить:** локальные данные удаляются, как при выходе → полная загрузка облака.
- Вход другим Apple ID — только после выхода.

### 2.4. Ручной выход (кнопка «Выйти») [У]

Только по явному действию пользователя. Никакое серверное событие (в том числе `consent-revoked`) этот сценарий не запускает.

1. Одно предупреждение об удалении локальных данных; в нём же — сколько несинхронизированных изменений будет потеряно. Варианта «Синхронизировать и выйти» нет.
2. После подтверждения — сразу, без синхронизации, одной локальной транзакцией: удаляются локальные финансовые данные (расходы), категории и состояния системных категорий, отметки дня, outbox, sync state, черновик импорта и настройки аккаунта. Общие настройки устройства сохраняются. Облачные данные сохраняются.
3. `POST /v1/auth/logout` — best-effort; без сети отзыв повторится при следующем запуске.
4. Возврат в гостевой режим с той же записью устройства.
5. Флаг `pending_local_wipe`: прерванная очистка завершается при следующем запуске.

### 2.5. Удаление аккаунта [У + Т]

**API:**

```
DELETE /v1/account     (токен аккаунта; тело опц.: { authorizationCode } — свежий код Apple)
  → 202 { deletionId, state }        повтор → тот же deletionId
GET /v1/account/deletions/{deletionId}   (гостевой токен ТОГО ЖЕ устройства, did совпадает)
  → 200 { state: pending | revoking | deleting | done | failed_retrying, updatedAt }
```

**Задание `deletion_jobs(deletion_id, user_id, requested_by_did, state, step, cursor, attempts, lease_until, last_error_code)`:**

1. **Синхронно в запросе `DELETE`:**
   - создать задание (идемпотентно по `user_id`);
   - `users.state = deleting`;
   - пометить refresh-токены аккаунта `revoked_reason = account_deleted`;
   - записать `deleted_accounts(user_id, deleted_at)`.

   С этого момента любой запрос с токеном аккаунта → `401 account_deleted`. Затем попытка выполнить шаги ниже в пределах ~5 с; не успели — `202`, продолжит фоновое задание.
2. **`revoking` — отзыв Apple-токена** ([Apple: revoke tokens](https://developer.apple.com/documentation/signinwithapplerestapi/revoke-tokens)):
   - запрос: `POST https://appleid.apple.com/auth/revoke`, `application/x-www-form-urlencoded`;
   - параметры: `client_id` (bundle id), `client_secret`, `token` (расшифрованный refresh token), `token_type_hint=refresh_token`;
   - `client_secret` — ES256 JWT: `kid` и `.p8` из Lockbox, `iss` = Team ID, `sub` = `client_id`, `aud = https://appleid.apple.com`, `exp` = 5 минут (Apple допускает до 6 месяцев; храним короткоживущим);
   - `200` (в том числе «токен уже недействителен») → шаг выполнен. Повтор безопасен;
   - `400 invalid_client` (ошибка нашей конфигурации) → повтор с backoff и алерт;
   - сеть или `5xx` → повтор с backoff;
   - **нет сохранённого токена или он отвергнут как невалидный** → использовать `authorizationCode` из тела `DELETE`. iOS получает его повторной авторизацией Apple на экране удаления. Обмен кода на токены, затем отзыв;
   - если кода нет — `revoke_skipped_no_token` в задании. Удаление данных продолжается, клиент показывает подсказку «отключите приложение в настройках Apple ID»;
   - отзыв не блокирует удаление данных: шаги 2 и 3 независимы, задание завершается после обоих.
3. **`deleting`:**
   - по таблицам в фиксированном порядке (`sync_records`, `sync_mutations`, `sync_state`, `import_ledger` и счётчики аккаунта, `apple_tokens`, `identities`, отвязка `devices.account_id`, `users`) пачками до 1 000 строк на транзакцию (лимиты транзакций YDB);
   - курсор `(step, cursor)` сохраняется после каждой пачки;
   - refresh-токены аккаунта **не удаляются** до истечения: в них только хэш, family и наш UUID пользователя, они нужны, чтобы `/auth/refresh` отвечал `account_deleted`, а не `refresh_token_invalid`. Их очищает задача по `expires_at`.
4. **Фоновое продолжение:**
   - timer trigger раз в 5 минут вызывает `/internal/deletions/run`;
   - берёт задания с `lease_until < now`, ставит аренду на 2 минуты, выполняет шаги, сохраняет прогресс;
   - повтор с экспоненциальной задержкой до 1 ч;
   - алерт, если задание старше 24 ч.
5. **`deleted_accounts`** хранит только наш UUID и дату, без Apple `sub` и без данных. Записи удаляются через 400 дней (дольше жизни refresh-токена — 365 дней). HMAC Apple ID ради квот **не хранится** [У].
6. **Будущие платежи** (не реализуем): российский платёжный сервис — шаг «отменить автопродление» перед `deleting`; App Store — предупреждение и `AppStore.showManageSubscriptions` на iOS до удаления.

**Клиент:**
- инициатор: после `202` сразу выполняет локальную очистку (как при выходе) → гостевой режим;
- статус при желании проверяет `GET /v1/account/deletions/{id}` гостевым токеном устройства;
- **другие устройства:** `401 account_deleted` → сообщение «Аккаунт удалён» → локальная очистка без предупреждения → гостевой режим.

### 2.6. Уведомления Sign in with Apple (server-to-server) [У + Т]

Официальные типы событий ([Apple: Processing changes for Sign in with Apple accounts](https://developer.apple.com/documentation/signinwithapple/processing-changes-for-sign-in-with-apple-accounts)): `email-disabled`, `email-enabled`, `consent-revoked`, `account-deleted`.

- **Эндпоинт:** `POST /v1/apple/notifications`, тело `{"payload": "<JWS>"}`. Проверка подписи по JWKS Apple (алгоритм из `alg`), `iss = https://appleid.apple.com`, `aud = bundle id`. Тип — `events.type`; claim `events` разбирается и как объект, и как JSON-строка. Ответ `200` после надёжной записи события.
- **Идемпотентность** по `jti` (иначе `(sub, type, event_time)`). Дубли — no-op `200`.
- **Реакции:**
  - **`consent-revoked`** → завершить все сессии аккаунта: отзыв refresh family, `revoked_reason = session_revoked`; устройства получают `401 session_revoked` [У];
  - **`account-deleted`** → удаление аккаунта (§2.5) без шага отзыва: Apple ID уже удалён [У];
  - `email-enabled` / `email-disabled` → `200`, без действий (email не храним);
  - неизвестный тип → `200` и запись в лог для анализа.

  Для устойчивости `account-delete` принимается как синоним: в сторонних источниках встречается такое написание.
- **Клиент при `session_revoked` [У]:** сессия и синхронизация прекращаются, **локальные данные, outbox и sync state не удаляются**; показывается необходимость повторного входа (§2.9). Это не выход: §2.4 не выполняется.

### 2.7. Неактивность [У]

- **Apple-аккаунты в MVP автоматически не удаляются** [У]. Отслеживание неактивности аккаунтов, предупреждения и задание удаления — после MVP, отдельным решением.
- **Гостевые технические записи** (`devices` и их refresh-токены, счётчик импортов устройства) удаляются через 12 месяцев с последнего запроса устройства, без предупреждения: данных пользователя в них нет.
  - Устройство, вошедшее в аккаунт, остаётся активным: `last_seen_at` обновляется по claim `did` (§2.2), а связь `devices.account_id` защищает запись, пока аккаунт существует.
  - Если удалённое устройство вернётся, оно получит `401 refresh_token_invalid` на гостевом refresh и создаст новую запись. Счётчик импортов устройства начнётся заново — это приемлемо после 12 месяцев простоя.

### 2.8. Коды 401 и поведение клиента [Т]

| Код | Когда | Клиент |
|---|---|---|
| `token_expired` | истёк access JWT | `/auth/refresh`, повтор запроса |
| `refresh_token_invalid` | неизвестный, отозванный при reuse detection, истёкший refresh | гость: создать новую гостевую запись; аккаунт: состояние «нужен повторный вход» (§2.9), данные сохраняются |
| `session_revoked` | `consent-revoked`, ручной отзыв сессий | состояние «нужен повторный вход» (§2.9), данные и outbox сохраняются |
| `account_deleted` | аккаунт удаляется или удалён (`deleted_accounts`, `revoked_reason`) | локальная очистка → гостевой режим |

### 2.9. Повторный вход после отзыва сессии [У + Т]

Состояние клиента `reauth_required` (после `session_revoked` или `refresh_token_invalid` у аккаунта) хранится локально и переживает перезапуск:
- outbox, cursor, horizon, resync state, локальные данные и `accountId` последнего аккаунта сохраняются;
- sync приостановлен: новые локальные изменения продолжают попадать в outbox;
- гостевые технические запросы (импорт) выполняются гостевым токеном устройства;
- баннер «Войдите снова, чтобы продолжить синхронизацию» не блокирует работу с локальными данными и аналитикой.

Повторный вход — тот же `POST /v1/auth/apple`. Сервер выдаёт новые токены и, если пришёл новый `authorizationCode`, заменяет сохранённый Apple refresh token. Клиент сравнивает `accountId` из ответа с сохранённым:

| Результат | Действие клиента |
|---|---|
| **тот же аккаунт** | `reauth_required` снимается; **диалог «Объединить / Заменить» не показывается** (это продолжение той же синхронизации); outbox отправляется как есть с прежними `mutationId` и `baseVersion` по обычным правилам конфликтов; затем pull с сохранённого cursor/horizon. Если горизонт успел сдвинуться — обычный resync после `410` с сохранением outbox (§3.1). Неподтверждённые изменения не теряются: идемпотентность по `mutationId` защищает от дублей, если часть outbox была принята до отзыва |
| **другой аккаунт** | данные прежнего аккаунта не смешиваются с новым: показывается предупреждение ручного выхода (§2.4) с числом неотправленных изменений; после подтверждения — очистка, затем вход в новый аккаунт по §2.3. Отказ — остаёмся в `reauth_required` |
| `account_deleted` | локальная очистка (§2.5) → гостевой режим |

Если `consent-revoked` пришёл во время выполнения push, принятые сервером мутации сохранены в журнале: повтор той же пачки после входа вернёт сохранённые результаты (`replayed`).

### 3.2. Категории [У + Т]

- Системные категории архивируются наравне с пользовательскими, **кроме резервной «Другое»** (`…000099`). Архивирование не удаляет категорию и не меняет историю. Архивные не предлагаются для новых расходов, связь существующих расходов сохраняется. UUID стабильны. Разархивирование — после MVP.
- **Модель без дублирования:** одна сущность `category`, один UUID, два вида payload:

  ```
  user:   { kind: "user",   name: 1–24, emoji: 1 графема, colorIndex: 0–11, sortOrder?, isArchived }
  system: { kind: "system", isArchived }        ← определение — константа приложения, в sync только состояние
  ```

  Реестр `SYSTEM_CATEGORY_IDS` ведётся в контракте. Пока пользователь не менял системную категорию, записи нет.

  Сервер отклоняет (`rejected/invalid`):
  - `kind=system` для id вне реестра;
  - `kind=user` с системным id;
  - смену `kind`;
  - `op=delete`;
  - `isArchived=true` для «Другое».

  Конкурентное архивирование системной категории сходится к одной записи (archive wins).
- **Ссылки расходов:**
  - на архивную категорию — сохраняются, с пометкой;
  - на ещё не полученную — плейсхолдер до завершения загрузки, FK на клиенте нет;
  - на неизвестную системную категорию — плейсхолдер. Сервер связи не проверяет.

### 3.3. Комментарий расхода [У + Т]

- Максимум **200** символов для ручных и импортированных расходов. Длинное название операции обрезается, операция не исключается.
- **Подсчёт:** NFC; удаление управляющих символов (Cc, кроме пробела); обрезка пробелов по краям; пустая строка → `null`. Длина — число Unicode scalar values: Python `len(s)`, Swift `s.unicodeScalars.count`. Эмодзи: 😀 = 1, 👍🏽 = 2, 👨‍👩‍👧 = 5.
- **Обрезка** (импорт на сервере, вставка на iOS): наибольший префикс из целых графем, не длиннее 200 кодовых точек. Server — модуль `regex` (`\X`), iOS — `Character`.
- **Sync** не обрезает, а отклоняет (`rejected/invalid`).
- **Исправить в E3:** `op.description[:COMMENT_MAX]` режет эмодзи. Лимит прототипа 500 → 200.

## 4. «День без расходов» (`day_mark`) [У]

- `entityId = UUIDv5(NS_DAY_MARK, "YYYY-MM-DD")`, payload `{ date, isMarked }`.
- `op=delete` запрещён: снятие отметки — `isMarked=false`.
- Сервер проверяет `entityId ↔ date` и `date ≤ серверное сегодня + 1`.
- **Вычисление:** `день отмечен пустым = isMarked && нет живых расходов на дату`.
- **Правило очистки:** устройство, увидевшее живой расход на дату с `isMarked=true`, записывает `isMarked=false`. После удаления последнего расхода отметка автоматически не восстанавливается.

| Сценарий | Итог |
|---|---|
| Отметил, потом добавил расход | расход; `isMarked=false` |
| Удалён последний расход дня | день не учтён; отметку ставят заново |
| Повторная установка | правка той же записи, без tombstone |
| A офлайн отмечает, B офлайн добавляет расход на ту же дату | расход виден, отметка игнорируется, затем очищается |
| A и B офлайн отмечают одну дату | одна запись (общий id), LWW |
| A отмечает, B снимает конкурентно | LWW |
| Объединение с облаком | общие id → LWW, затем правило очистки |

## 6. Импорт выписок

### 6.1. Учёт: 3 бесплатных подтверждённых импорта [У + Т]

- Импорт засчитывается после **успешного разбора на backend и подтверждённого показа результата на iOS**.
- Сохранение и удаление черновика счётчик не меняют; ошибки разбора и недоставленные результаты попытку не расходуют; повторное подтверждение одного `importId` идемпотентно; до Premium импорт после исчерпания не блокируется. Импорт доступен гостю. [У]
- **Модель учёта — уникальные подтверждённые импорты без двойного учёта [У + Т]:**
  - `import_ledger(import_id PK, device_id, account_id?, attributed_account_id?, confirmed_at)` — **постоянная** запись о каждом подтверждённом импорте. Только метаданные: ни операций, ни сумм, ни описаний, ни имени файла;
  - `account_id` — аккаунт, под которым был разбор (`null` у гостя);
  - `attributed_account_id` — аккаунт, которому засчитан гостевой импорт: заполняется **один раз**, при первом входе устройства в аккаунт;
  - **счётчик устройства** `used_device(D)` = число записей с `device_id = D`, всех импортов на устройстве, гостевых и под аккаунтом;
  - **счётчик аккаунта** `used_account(A)` = число записей с `account_id = A` или `attributed_account_id = A`;
  - для O(1) поддерживаются счётчики `usage_counters(subject, feature)`, обновляемые в той же транзакции, что вставка в реестр. Каждый `import_id` учитывается не больше одного раза на устройство и одного раза на аккаунт;
  - `/me` показывает гостю `used_device`, аккаунту — `used_account`. **После выхода** показывается `used_device`: он не сбрасывается и включает импорты, сделанные под аккаунтом на этом устройстве;
  - **удаление аккаунта:** записи с `account_id = A` и счётчик аккаунта удаляются. Счётчик устройства остаётся числом. Повторная регистрация тем же Apple ID начинает счётчик аккаунта с нуля: HMAC не храним [У].

### 6.2. API, повтор и подтверждение [Т]

```
POST /v1/imports/parse      multipart: file (≤ 2 МБ), categories (JSON), categoryHints (JSON, опц.)
                            Idempotency-Key: <UUID попытки импорта>
  → 200 { importId, confirmed: bool, parserVersion, bank, period, operations[], skippedIncomeCount, warnings[],
          imports: { used, limit } }
POST /v1/imports/{importId}/displayed
  → 200 { imports: { used, limit, state, enforced } }       (идемпотентно)
```

**Таблица `import_deliveries(device_id, idem_key, import_id, file_mac, account_id?, created_at, confirmed_at?)`**, PK `(device_id, idem_key)`, TTL **7 дней**:
- `file_mac = HMAC-SHA256(server_key, содержимое файла)` — необратимый отпечаток, а не данные;
- `import_id` — UUID, сгенерированный сервером при первом успешном разборе.

| Ситуация | Поведение |
|---|---|
| Новый ключ, разбор успешен | создать доставку, вернуть новый `importId`, `confirmed=false` |
| Новый ключ, ошибка разбора | доставку **не создавать**, `422 <код>`; повтор с тем же ключом разбирается заново |
| Тот же ключ, тот же файл (`file_mac` совпал), не подтверждён | **разобрать заново** (результат на сервере не хранится), вернуть **тот же** `importId`; новой доставки нет, счётчик не меняется |
| Тот же ключ, тот же файл, уже подтверждён | разобрать заново, тот же `importId`, `confirmed=true`; счётчик **не** увеличивается повторно |
| Тот же ключ, **другой** файл | `409 idempotency_key_reused`, разбор не выполняется |
| Тот же ключ, другие `categories` или подсказки | допустимо: результат пересчитывается, `importId` тот же |
| Ключ старше 7 дней (доставка истекла) | как новый ключ: новый `importId` |
| Параллельный запрос с тем же ключом | `409 idempotency_in_progress` + `Retry-After` |

- Клиент генерирует ключ **один раз на попытку импорта** (выбор файла) и повторяет с ним все сетевые попытки (§8.1). Новый выбор файла — новый ключ.
- **Что гарантирует повтор:**
  - тот же `importId`; счётчик учитывает импорт не больше одного раза;
  - операции (дата, сумма, нормализованный комментарий) совпадают при той же версии парсера (поле `parserVersion` в ответе).
- **Что повтор не гарантирует:** **набор предложенных категорий может отличаться.** Результаты категоризации на сервере не хранятся, а повторная обработка может дать другой ответ LLM, обновлённые правила или другие `categories` и подсказки. Клиент не полагается на совпадение категорий между ответами (§6.5).

**Подтверждение показа** вызывается после того, как экран проверки результата показан пользователю. Сервер в одной транзакции:
- доставка найдена по `import_id` и `device_id` токена совпадает с её `device_id` (подтверждает устройство, которое показало результат; гостевой токен или токен аккаунта этого устройства);
- `confirmed_at` пуст → поставить его, вставить запись в `import_ledger` (`account_id` — из доставки, то есть по контексту на момент разбора), обновить счётчики;
- уже подтверждена → no-op, тот же ответ;
- нет доставки с таким `import_id` для этого устройства → `404`;
- доставка истекла (старше 7 дней, удалена по TTL) → `410 delivery_expired`, попытка не расходуется.

Клиентская очередь подтверждений хранит `importId` до успеха или `404` / `410` и повторяет с backoff независимо от экрана (§8.1).

**Неподтверждённые результаты:** не больше `IMPORT_UNCONFIRMED_MAX` (3) неподтверждённых доставок, созданных за последние 24 ч, на устройство → `429 unconfirmed_imports_limit`. Повторы с тем же ключом новых доставок не создают и в лимит не входят.

### 6.4. AI только при необходимости [У + Т]

Банковский формат разбирает детерминированный парсер: AI в разборе не участвует. AI — последняя ступень категоризации:
1. правила сервера (`categorization.rule_match`);
2. подсказки клиента `categoryHints` — до 500 пар `{merchantKey, categoryId}` из истории устройства, на сервере не хранятся;
3. LLM (YandexGPT Lite, маскированные описания) — только для нераспознанных шагами 1–2, одним батчем, не больше `AI_MAX_DESCRIPTIONS_PER_IMPORT`;
4. AI выключен, недоступен или ответил ошибкой → `needs_review`. Импорт не падает.

### 6.5. Клиентский контракт черновика импорта [Т]

Черновик живёт только на устройстве, его ключ — `importId`.

| Ситуация | Поведение iOS |
|---|---|
| Первый успешный ответ | создать локальный черновик `draft(importId, operations, suggestedCategories, parserVersion)` и показать экран проверки. Событие показа в той же локальной транзакции ставит подтверждение `importId` в надёжную очередь (§6.2) |
| Ответ потерян (таймаут, обрыв) | черновика нет; экран остаётся на скелетоне и повторяет запрос с **тем же** `Idempotency-Key` по §8.1. Получен ответ — создать черновик как при первом ответе |
| Повтор вернул `importId`, для которого **черновик уже существует** | **черновик не перезаписывается**: правки пользователя, выбранные категории, удалённые строки сохраняются. Новый ответ используется только для `confirmed` и `imports`, его операции и категории отбрасываются |
| Повтор вернул `confirmed=true`, а черновика нет (например, его удалили) | черновик создаётся заново из ответа; подтверждение не требуется, счётчик не меняется |
| Пользователь открыл черновик и вернулся к выбору того же файла | это новая попытка: новый ключ, новый `importId`, отдельный черновик. Повторные импорты не проверяются на дубликаты [У]; после показа она засчитывается как отдельный импорт |
| Черновик сохранён в расходы или удалён | счётчик не меняется [У]; повторных запросов по этому `importId` нет |
| Экран закрыт до ответа | запрос и повторы отменяются (§8.1). Если сервер уже разобрал файл, доставка остаётся неподтверждённой и попытку не расходует |

## 7. Алгоритмическая аналитика (MVP: локально, бесплатно, без AI и интернета) [У + Т]

### 7.1. Принципы

- **Где считается:** на iOS из локальной БД, полностью офлайн. Работает у гостя и у аккаунта. Не обращается к сети, **не показывает сообщений об интернете** и не ждёт sync: считает по тому, что есть локально. Сервер аналитику не считает и не хранит. AI и LLM не используются.
- **Все виды сразу:** каждый из 9 видов возвращает `status: ready | insufficient_data | empty`.
  - Пользователь видит **все** виды со статусом `ready`.
  - `insufficient_data` содержит причину и недостающий объём («нужно ещё 9 учтённых дней»).
- **Эталон:** формулы ниже — спецификация. Python-эталон и тест-векторы (A1) — общий эталон для iOS и будущего Android. Версия спецификации `analytics_spec_version = 1`. Пороги утверждены как стартовые [У] и хранятся в одном конфигурационном объекте приложения, версионируемом вместе со спецификацией.

### 7.2. Арифметика и детерминированность

| Правило | Определение |
|---|---|
| Деньги | целые копейки (`Int64`): максимум суммы расхода 99 999 999 999 коп.; сумма даже миллиона расходов помещается в `Int64` |
| Деления | точные: `Decimal` с точностью ≥ 28 значащих цифр (Python `decimal`, Swift `Decimal`); промежуточные результаты **не округляются** |
| Сравнение с порогами | по неокруглённым значениям |
| Округление при выводе | половина — от нуля (`ROUND_HALF_UP` в Python; `.plain` в Swift, для положительных чисел совпадает): суммы — до копейки, проценты — до 0,1 |
| Доли в распределении | метод наибольшего остатка, сумма ровно 100,0 %; при равных остатках — большая сумма, затем `categoryId` |
| Медиана | отсортировать; нечётное `n` — средний элемент; чётное — среднее двух центральных (точно) |
| Квартили `q25` / `q75` | линейная интерполяция между ближайшими рангами (метод 7 по Hyndman–Fan, как `numpy.quantile` по умолчанию): `h = (n − 1)·p`, `q = x[⌊h⌋] + (h − ⌊h⌋)·(x[⌊h⌋+1] − x[⌊h⌋])`, индексация с 0 |
| `MAD` | `median(|xᵢ − median(x)|)`, масштаб `1,4826` |
| Средний месяц | константа `MONTH = 30,4375` (= 365,25 / 12) дня. «В среднем за месяц» = значение на день × `MONTH`. Число 30 нигде не используется |
| Неделя | ISO: понедельник — первый день; день недели 1–7 |
| Порядок при равенстве | сумма ↓, затем дата ↑, затем `categoryId` ↑ (лексикографически) |
| Доля «не меньше k из n» | `⌈k · n⌉` целых, например «≥ 2/3 из 2» = 2 |

### 7.3. Общие определения

| Термин | Определение |
|---|---|
| Расход | живой (не удалённый) `Expense`, `amount > 0`, календарная дата `date ≤ сегодня` |
| «Сегодня» | календарная дата в текущем часовом поясе устройства; даты расходов календарные и при смене пояса не пересчитываются |
| Период `P = [a, b]` | включительно. Пресеты: неделя (пн–вс), месяц, квартал, год, произвольный |
| Прошедшая часть | `P* = [a, min(b, сегодня)]`, включая сегодняшний день |
| Полный период | `b < сегодня` |
| Неполный период | `b ≥ сегодня`; все расчёты — по `P*` |
| Учтённый день | дата с хотя бы одним расходом **или** с отметкой «без расходов», действующей по §4 (такой день = 0 ₽). Неучтённый день — неизвестность, а не ноль |
| `D(P)` / `C(P)` | число учтённых / календарных дней в `P*` |
| Покрытие | `cov(P) = D(P) / C(P)` |
| `T(P)`, `T_c(P)` | сумма расходов в `P*`, общая и по категории `c` |
| Категории | по `categoryId`, включая архивные; неизвестные → «Без категории» |
| Фильтр категории | числитель — по категории, знаменатель (учтённые дни) — общий |
| Пометка «данные неполные» | при `cov < 0,6` у любого участвующего периода |

### 7.4. Девять видов аналитики

#### 1. Сравнение расходов за периоды

- `Q` — по умолчанию предыдущий период того же типа; для произвольного `P` — `[a − |P|, a − 1]`. Доступны «год назад» и произвольный.
- **Неполный `P` — «на ту же дату»:** `k = C(P)` (прошедших дней, включая сегодня), `Q' = [a_Q, min(a_Q + k − 1, b_Q)]`. Для месяцев это день месяца с отсечением по концу более короткого месяца: 30 марта → `Q' = 1–28 февраля`. Полный `P` → `Q' = Q`.
- **Формулы:**
  - `Δ = T(P) − T(Q')`;
  - `Δ% = Δ / T(Q') · 100` при `T(Q') > 0`, иначе `null` («ранее расходов не было»);
  - дополнительно средние на учтённый день: `A(P) = T(P)/D(P)`, `A(Q') = T(Q')/D(Q')`, их разница и `%`.
- **Минимум:** `D(P) ≥ 1`, `D(Q') ≥ 1`, иначе `insufficient_data`.
- **Пограничные:** `T(Q') = 0` при `D(Q') > 0` → «было 0 ₽»; пометка «данные неполные».

#### 2. Распределение и сравнение по категориям

- `share_c = T_c(P) / T(P)`; сортировка по `T_c` ↓; отображаемые проценты — методом наибольшего остатка.
- `count_c` и средний чек `T_c / count_c`.
- **Сравнение** с тем же `Q'`:
  - `Δ_c = T_c(P) − T_c(Q')`;
  - `Δ%_c` — как в п. 1;
  - сдвиг доли `share_c(P) − share_c(Q')` в п.п.;
  - категории только из `Q'` → `T_c(P) = 0` («перестали тратить»); только из `P` → «новая», `Δ% = null`.
- **Минимум:** `T(P) > 0`, иначе `empty`; сравнение — при `D(Q') ≥ 1`.

#### 3. Средние расходы за день и за период

- **День:** `A_day(P) = T(P)/D(P)`; `A_wd`, `A_we` — по учтённым будням и выходным; медиана дневных сумм учтённых дней.
- **Период:** для каждого из последних `K` полных периодов того же типа (по умолчанию 3 месяца или 4 недели) с `cov ≥ 0,6` — оценка полного периода `T_full(i) = T(i) / D(i) · C(i)`: неучтённые дни заполняются средним этого же периода, при полном покрытии `T_full = T`. Средний период — `mean(T_full(i))`. Исключённые периоды перечисляются.
- **«В среднем за месяц»** из дневного среднего: `A_day · MONTH`.
- **Минимум:** `A_day` — `D(P) ≥ 3`; средний период — ≥ 2 подходящих полных периода.
- **Пограничные:** `D = 0` → `empty`; только отметки «без расходов» → `A_day = 0`, `ready`.

#### 4. Самые дорогие календарные даты

- `T(d)` по дням `P*` с расходами; топ-`N` (5) по `T(d)` ↓, при равенстве — более ранняя дата.
- Для каждой даты: сумма, число расходов, главная категория (`max T_c(d)`, при равенстве — по `categoryId`). Пометка «за счёт одной покупки», если крупнейший расход `> 0,5 · T(d)`.
- **Минимум:** 1 день с расходами; если дней меньше `N`, показываются все. Дни-отметки в рейтинг не входят.

#### 5. Дни недели (нормализация по числу соответствующих дней)

- **Окно:** последние 84 дня до сегодня включительно (12 недель) или выбранный период ≥ 28 дней.
- **Для дня недели `w`:** `N_w` — число **учтённых** дней `w` в окне; `S_w` — их сумма; **`avg_w = S_w / N_w`**.
- `avg = Σ_w S_w / Σ_w N_w`; индекс `I_w = avg_w / avg` (при `avg > 0`).
- Самый затратный и экономный день — `argmax` / `argmin` `avg_w` среди дней с `N_w ≥ 3`; при равенстве — меньший номер дня.
- **Вклад категорий** — точное разложение:
  - `avg_w − avg = Σ_c (S_{c,w}/N_w − S_c/Σ N)`, где `S_c = Σ_w S_{c,w}`;
  - главные вклады — наибольшие положительные слагаемые;
  - структура дня — `S_{c,w}/S_w`.
- **Минимум:** окно ≥ 28 дней и `N_w ≥ 3` хотя бы для 5 дней недели. Дни с `N_w < 3` → «мало данных», в сравнении не участвуют.
- **Пограничный:** если один расход `> 0,4 · S_w` → пометка «определяется разовой покупкой» и медиана дневных сумм этого дня недели.

#### 6. Тренды расходов по категориям

- **Ряд:** последние `K` полных месяцев (по умолчанию 6, минимум 3); текущий неполный месяц не входит.
- `x_i = T_c(i) / D(i) · MONTH` — расход категории в пересчёте на средний месяц по учтённым дням. Месяцы с `cov < 0,6` исключаются; осталось меньше 3 → `insufficient_data`. Индекс `i` — порядковый номер месяца (пропуски сохраняют реальные номера).
- **Наклон Тейла — Сена:** `slope = median{ (x_j − x_i)/(j − i) : i < j }`.
- `r = slope / median(x)` при `median(x) > 0`.
  - **Рост:** `r ≥ 0,10` и положительных последовательных изменений `≥ ⌈2/3 · (n − 1)⌉`.
  - **Снижение:** `r ≤ −0,10` и отрицательных `≥ ⌈2/3 · (n − 1)⌉`.
  - Иначе — стабильно.
- **Значимость:** `median(x) ≥ 0,03 · median(X)` (где `X` — тот же ряд по всем расходам) или `≥ 500 ₽`.
- **Вывод:** топ-3 растущих и снижающихся по `|slope|` и ряд для графика.
- **Пограничные:** категория появилась недавно → только месяцы с её присутствием (≥ 3), иначе «новая категория»; `median(x) = 0` → `r` не считается.

#### 7. Повторяющиеся платежи и регулярные траты

- **Ключ группы:** `merchantKey(comment)` + `categoryId`.
  - `merchantKey`: NFC → нижний регистр → удалить цифры, маски карт, знаки валют и пунктуацию → схлопнуть пробелы → первые 40 кодовых точек.
  - Без комментария — `(categoryId, amount)`, только точное совпадение суммы.
- **Повторяющийся платёж:**
  - ≥ 3 расходов группы за последние 395 дней (13 мес.); для годовых ≥ 2;
  - интервалы `Δ_i` между соседними датами, `m = median(Δ)`;
  - **каденция по `m`:** неделя `[6; 8]`, 2 недели `[12; 16]`, месяц `[27; 34]`, квартал `[84; 98]`, год `[355; 375]` дней; вне диапазонов — не повторяющийся;
  - **регулярность:** интервалов внутри диапазона каденции `≥ ⌈2/3 · (n − 1)⌉`;
  - **сумма:** «фиксированная», если все суммы в пределах ±10 % от медианы, иначе «переменная» (min–max);
  - **следующая дата:** неделя, 2 недели — последняя дата + 7 / 14; месяц, квартал, год — тот же день месяца через 1 / 3 / 12 месяцев с отсечением по концу месяца (31 янв → 28/29 фев);
  - **допуск:** 2 / 3 / 5 / 10 / 15 дней. `сегодня > следующая + допуск` → «возможно, отменён или пропущен»; после 2 пропущенных циклов — неактивен;
  - **месячная нагрузка:** `Σ median(amount) · f` по активным, `f` = `MONTH/7`, `MONTH/14`, `1`, `1/3`, `1/12`.
- **Регулярная трата** (не повторяющийся платёж): группа с ≥ 8 расходами за последние 60 дней. Вывод: частота в месяц `= n / 60 · MONTH`, средний чек, сумма в пересчёте на месяц, доля в расходах.
- **Минимум истории:** 3 платежа (2 интервала) для недели, 2 недель, месяца и квартала; 2 платежа (1 интервал) для года; регулярные — 8 расходов за 60 дней.
- **Пограничные:** две одинаковые подписки дают `m ≈ 15` → «2 недели», пометка «проверьте»; смена цены подписки → «переменная».

#### 8. Необычно крупные расходы и отклонения

- **Крупный расход в категории** (оценивается каждый расход последних 30 дней):
  - выборка — расходы категории за 180 дней **до даты** расхода, без повторяющихся платежей п. 7; нужно `n ≥ 8`;
  - `z = (x − med) / (1,4826 · MAD)`;
  - «необычно крупный», если `z ≥ 3,5` **и** `x ≥ 2 · med` **и** `x ≥ max(1 000 ₽; 0,5 · A_day)`, где `A_day` — по учтённым дням тех же 180 дней;
  - `MAD = 0` → условие `x ≥ 3 · med` и тот же абсолютный порог;
  - `n < 8` → выборка всех расходов за 180 дней (`n ≥ 30`), `z ≥ 4`;
  - иначе не оценивается.
- **Необычный день:** дневная сумма учтённого дня против медианы и `MAD` дневных сумм учтённых дней за 90 дней до него (≥ 20 дней), `z ≥ 3,5`, тот же абсолютный порог.
- **Отклонение категории в текущем периоде:**
  - `x_cur = T_c / D · MONTH` при `D ≥ 7`;
  - сравнение с медианой `x_i` (п. 6) за 3–6 полных месяцев;
  - «больше обычного» при `x_cur / med ≥ 1,5` и `x_cur − med ≥ 1 000 ₽`;
  - «меньше обычного» при `x_cur / med ≤ 0,5` и `med − x_cur ≥ 1 000 ₽`.
- **Новая категория трат:** первая трата в категории за 180 дней — тип «новое», не аномалия.
- **Минимум:** 30 учтённых дней за последние 180. Повторяющиеся платежи п. 7 не оцениваются и в выборки не входят.

#### 9. Прогноз расходов до конца месяца

- **Обозначения:** месяц `M` из `L` дней, сегодня — день `t`.
  - `S = T([1, t])` — включая сегодня (сегодняшний день считается прошедшим);
  - очищенные дневные суммы `y(d)` — дневные суммы учтённых дней за последние 56 дней до сегодня (без текущего дня), **без** повторяющихся платежей п. 7 и необычных расходов п. 8;
  - для дня недели `w`: `v_w = mean(y)` по учтённым дням `w` при `N_w ≥ 2`, иначе общий `v = mean(y)`;
  - квартили `q25_w`, `q75_w` по тем же значениям при `N_w ≥ 4`, иначе общие `q25`, `q75`;
  - `R_left` — медианные суммы активных повторяющихся платежей с ожидаемой датой в `(t, L]`, ещё не оплаченных в `M` (нет расхода группы в `M` после предыдущей ожидаемой даты).
- **Прогноз:** `F = S + R_left + Σ_{d=t+1..L} v_{w(d)}`.
- **Диапазон:**
  - `F_low = min(F, S + R_left + Σ q25_{w(d)})`;
  - `F_high = max(F, S + R_left + Σ q75_{w(d)})`.

  `min` и `max` гарантируют `F_low ≤ F ≤ F_high` при асимметричных данных.
- **Сравнение:** с прошлым месяцем и со средним периодом п. 3; «если так продолжится — на X ₽ больше/меньше обычного».
- **Минимум:** ≥ 14 учтённых дней за последние 56, иначе `insufficient_data`.
- **Пограничные:**
  - `t = L` → `F = F_low = F_high = S`;
  - `t ≤ 3` → пометка «ранний прогноз»;
  - `cov([1, t]) < 0,7` → «прогноз может быть занижен: не все дни учтены»;
  - нет повторяющихся платежей → `R_left = 0`;
  - сегодняшние расходы ещё не внесены → `S` занижена (покрывается той же пометкой).

### 7.5. Сводка минимальных требований

| # | Вид | Минимум данных |
|---|---|---|
| 1 | Сравнение периодов | по 1 учтённому дню в `P*` и `Q'` |
| 2 | Категории | `T(P) > 0`; сравнение — + 1 учтённый день в `Q'` |
| 3 | Средние | 3 учтённых дня; средний период — 2 полных периода с покрытием ≥ 60 % |
| 4 | Дорогие даты | 1 день с расходами |
| 5 | Дни недели | окно ≥ 28 дней; `N_w ≥ 3` для ≥ 5 дней недели |
| 6 | Тренды | 3 полных месяца с покрытием ≥ 60 % |
| 7 | Повторяющиеся / регулярные | 3 платежа нужной каденции (год — 2); регулярные — 8 за 60 дней |
| 8 | Отклонения | 30 учтённых дней за 180; выборка категории ≥ 8 (или всех ≥ 30) |
| 9 | Прогноз | 14 учтённых дней за последние 56 |

### 7.6. Тест-векторы (A1)

- **Формат.** Вход — `{ specVersion, today, timezone, expenses[{id, amountMinor, date, categoryId, comment, deleted}], dayMarks[{date, isMarked}], categories[{id, kind, isArchived}], params }`. Выход — по каждому виду `{ status, reason?, values }`. Суммы — строками в копейках, доли — строками с точностью вывода и неокруглёнными значениями, необходимыми для проверки порогов.
- **Обязательные случаи для каждого вида (≥ 10 на вид):**
  - пустые данные;
  - ровно на минимуме и на единицу ниже минимума;
  - неполный текущий период;
  - конец месяца: 31-е → февраль, високосный 29 февраля;
  - смена часового пояса устройства (даты не сдвигаются);
  - удалённые расходы (исключены);
  - отметка «без расходов» на дату с расходом (расход главнее);
  - архивная и неизвестная категория;
  - равенство значений (порядок);
  - граница округления `…,005`;
  - максимальные суммы (переполнения нет).
- **Специфичные случаи:**
  - **п. 3** — оценка `T_full` при неполном покрытии;
  - **п. 5** — `N_w < 3`, разовая покупка;
  - **п. 6** — пропущенный месяц, медиана 0;
  - **п. 7** — 31-е число, две одинаковые подписки, пропуск 1 и 2 циклов, переменная сумма;
  - **п. 8** — `MAD = 0`, `n < 8` → общая выборка, новая категория;
  - **п. 9** — `t = L`, `t ≤ 3`, низкое покрытие, асимметрия (`F` вне квартилей → `min`/`max`).
- **Детерминированность:** два прогона эталона дают побайтно одинаковый JSON; векторы проверяются в CI iOS.

## 8. Технические эндпоинты и сетевое поведение клиента

- **`/imports/parse`** — §6; **`/me`** — аккаунт, `features.imports`, `sync.lastVersion`.
- **Аналитических эндпоинтов нет:** `/analytics/*`, `/calendar/*`, `/insights` удаляются.

### 8.1. Сеть в UI [У + Т]

**Локальная аналитика, просмотр и ввод расходов, черновик импорта** работают полностью без интернета, без сообщений о сети.

**Сетевые экраны со скелетоном** — разбор выписки, вход через Apple, удаление аккаунта.

Состояния экрана: `loading` (скелетон) → `content` | `error` (с действием «Повторить»).

1. **Скелетон** отображается только пока выполняется запрос или идут автоматические повторы.
2. **Автоматические повторы** — только для повторяемых ошибок: нет сети, таймаут, `5xx`, `503`, `429`. Ограниченный exponential backoff с full jitter:
   - задержка перед попыткой `n` — случайная в `[0; min(16 с, 1 с · 2ⁿ⁻¹)]`;
   - не больше **4 повторов** (5 попыток всего);
   - общий бюджет — **≤ 45 с** с момента нажатия;
   - `Retry-After` от сервера соблюдается, если укладывается в бюджет, иначе сразу переход к ошибке.
3. **По исчерпании повторов** — понятное состояние ошибки вместо скелетона: «Нет соединения» или «Сервис временно недоступен» с кнопкой **«Повторить»**. Нажатие запускает новый цикл. Для разбора — с тем же `Idempotency-Key` (§6.2).
4. **Неповторяемые ошибки** (`4xx` кроме `429`: `413 file_too_large`, `422 unknown_bank`, `409` и др.) → сразу состояние ошибки с понятным текстом, без автоматических повторов.
5. **Уход с экрана** отменяет текущий запрос и все запланированные повторы этого экрана.
6. **Фоновые операции не привязаны к экрану и не отменяются уходом:**
   - подтверждение показа импорта, уже записанное в надёжную очередь (§6.2, §6.5);
   - отзыв сессии при `logout`.

   Они повторяются с backoff (тот же алгоритм, потолок задержки 15 мин, без ограничения числа попыток) до успеха или окончательного ответа (`404` / `410` для подтверждения).
7. **Sync** — фоновый: ошибки сети не показываются как ошибка экрана; повтор с тем же backoff (потолок 15 мин); статус синхронизации — неблокирующий индикатор.

Константы (`retry_max_attempts`, `retry_budget_s`, `retry_cap_s`) — в конфигурации клиента.

## 10. Персональные данные и логирование [Т]

- **Регион:** только `ru-central1`.
- **ПДн на сервере:** расходы и категории аккаунтов, Apple `sub`, шифротекст Apple-токена. Email и имя не храним. Реестр импортов — только id, устройство, аккаунт и время.
- **Логи — белый список:** маршрут, статус, длительность, `requestId`, HMAC субъекта, счётчики. **Никогда:** суммы, комментарии, названия категорий, содержимое и имена файлов выписок, payload, токены, коды Apple, IP в долговременных логах.
- **AI:** только маскированные описания и названия категорий; `x-data-logging-enabled: false`. Аналитика на сервер не уходит.
- **Удаление:** §2.5; `deleted_accounts` — только UUID и дата. Бэкапы YDB истекают через 2 дня — отразить в политике.
- **Доступ:** runtime — `ydb.editor`; DDL — отдельный сервисный аккаунт.
- **Правовая часть:** политика конфиденциальности и уведомление Роскомнадзора до релиза — нужна юридическая проверка.

## 14. После MVP

### 14.1. AI-инсайты [У]

- **30 дней бесплатного доступа** с первого *успешно отображённого* инсайта. Учёт серверный и идемпотентный, по образцу подтверждения импорта: `deliveryId`, `POST …/displayed`, `clamp(displayedAt)`, повторная доставка по `Idempotency-Key`.
- **Без** пользовательского лимита в 3 инсайта за пробный период.
- Объяснения финансовых изменений, персональные рекомендации, сценарии экономии, вопросы пользователя к своим расходам.
- После пробного периода — блюр блока, значок Premium, переход на экран Premium.
- Основа — агрегаты §7: числа считает алгоритм, LLM формулирует (проверка чисел `validate_item`).
- **Отдельно перед следующим релизом:** темы, периоды, отбор данных, содержание рекомендаций, модель, бюджет и защита от злоупотреблений.
- `app/modules/insights` удаляется в E11; при возвращении переиспользуются `ai/client.py` и проверка чисел.

### 14.2. Прочее

- Premium и оплата (§5).
- Политика неактивных Apple-аккаунтов: срок, канал предупреждения (email через Apple relay / push / в приложении), удаление тем же заданием, что §2.5.
- Разархивирование категорий.
- App Attest / DeviceCheck перед включением квот.
